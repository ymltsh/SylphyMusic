## 2. 已确认：第一版音乐源范围（S-001）

- **本地音乐**：Android / Windows / Linux 上的本地音乐文件。
- **Emby**：远程媒体服务器音乐库。
- **Navidrome / OpenSubsonic**：共用 Subsonic / OpenSubsonic 协议适配方向；按服务器能力判定具体接口支持情况。

Jellyfin、WebDAV、SMB、Plex、OpenList/AList、各类网盘不纳入第一版，但后续增加来源时不应要求重构播放内核。

## 3. 已确认：音乐库组织（S-002）

**采用混合模式（方案 C）**：

- 提供「统一音乐库」入口，汇总已启用音乐源的歌曲、专辑、歌手等记录；支持按来源/来源实例筛选（筛选的具体交互在 UI 评审时决定）。
- 同时提供「独立音乐源入口」，允许只浏览特定本地来源或服务器实例。
- 内部每条曲目仍保留其确切的来源实例身份与来源内条目 ID；统一列表只是展示聚合，不等于自动跨源合并同曲文件。
- 跨源去重展示 **S-006A 已确认独立展示、不自动合并**；S-006B/C 已确认收藏和本地/云端歌单设计。
- 可停用单个来源而不影响其他来源；被停用源是否仍展示离线内容，后续在离线策略评审时确认。
- **S-010A 已确认分类直达方案 A**：统一音乐库主入口直接提供 `歌曲 / 专辑 / 艺术家 / 歌单`，同时保留独立音乐源入口；不以最近播放等概览卡片作为必经首页，也不首版提供可切换的两套首页模式。分类初始选中页签、具体控件样式仍属于导航交互细节，尚未确认。
- **S-010B 已明确主要方向**：统一库的艺术家与专辑不强制按照 SourceProfile 分割展示；歌曲仍按 `TrackRef` 独立，不做自动去重；提供常见排序；手动黑名单已确认仅针对具体歌曲 `TrackRef`；列表/搜索/队列等具体生效边界仍待工程产品验收。来源筛选为辅助能力，不是进入艺术家/专辑的必经操作。

### 3.1 建议的基础身份模型（实现提案，非独立决策）

- `sourceProfileId`：客户端管理的来源连接实例 ID（本地生成的稳定 ID）。
- `remoteTrackId`：来源内部曲目 ID；对于本地文件采用独立稳定定位方式，后续评审。
- `TrackRef = (sourceProfileId, remoteTrackId)`：一条音频资源引用。
- 一台物理服务器可能有多个连接实例（不同账号），不能只用服务器 URL 或服务器 ID 作为唯一客户端身份。

## 4. 已确认：多服务器实例和独立账号（S-003）

### 4.1 多服务器实例

- 允许同时添加任意多个 Emby、Navidrome/OpenSubsonic 服务器实例，并使用自定义显示名称。
- 每个实例可独立启停，有自己的连接状态、认证信息、音乐库索引、同步状态及相关操作入口。
- 一台实际服务器可以添加多次；不同账号作为不同的 `SourceProfile`，不额外建设“服务器 → 子账号”的分层切换界面。
- 本地音乐在各设备上为设备专属来源；不假设 Android / Windows / Linux 的本地文件路径相同。

### 4.2 独立来源身份

- `sourceProfileId`：客户端本地生成的稳定连接配置 ID，用于区分“服务器 + 账号”组合，变更 URL 时保持不变。
- `serverId`：协议能提供时记录真实服务器标识，例如 Emby；仅用作关联与检查依据，不替代 TLS 或凭证验证。
- 凭据、用户可见数据、同步游标等按 `sourceProfileId` 隔离。
- 同一服务器不同账号不能由于 URL 或服务器 ID 相同就合并授权范围、收藏或音频缓存访问权。
- `TrackRef = (sourceProfileId, remoteTrackId)` 保留；后续的自动跨来源去重另行评审。

> 说明：S-003 确认的是实例与账号组织。具体登录协议、双地址和发现机制将在 S-004 / 认证安全专项核对。

## 5. 服务器连接设计（S-004）：A/B/C/D 均已确认

### 5.1 S-004A 已确认：单地址手动管理（方案 A）

- 每个服务器连接配置 (`SourceProfile`) **仅保存一个 `baseUrl`**，由用户手动输入、修改；可以是内网 IP、域名、公网地址或通过 VPN 可达的地址。
- **不实现**局域网 / 公网双地址字段、自动 LAN/WAN 选路、已配置端点之间的自动回退，亦不根据网络类型自动更改 URL。
- 每个实例的 `sourceProfileId` 保持稳定；地址修改时不直接清空本地播放队列和音乐库索引，但需要**重新验证服务器身份与当前账号授权**，验证失败时禁止将旧凭证发送至新主机或继续同步，避免错误关联不同服务器。
- 多台同类服务器和同台服务器不同账号仍按 S-003 的独立配置管理。一个来源连接只使用自己记录的 `baseUrl`，其他来源的 URL 不作为故障回退候选。
- HTTP 与 HTTPS 都可直接填写，不强制额外确认（S-004D-H3）。使用 HTTPS 时仍须严格执行证书链和主机名验证；不能通过跳过 TLS 验证实现恢复。

> 核心区分：**自动重连**是对同一配置 URL 重试或重新解析播放请求，**自动切换地址**则是从 LAN 改成 WAN。S-004A 只排除了后者，没有否定网络重连和播放器错误恢复。

### 5.2 S-004B 已确认（方案 C）：有限网络重试 + 音频播放恢复

- 对**可恢复的网络错误**进行有限次数自动重试，采用指数退避并加入抖动，区分音乐库 API、音频播放和用户发起批量缓存任务的重试预算。具体次数和超时由技术实现阶段根据设备测试确定，不在产品规格中硬编码。
- 保留已有播放器缓冲和已缓存数据；网络暂时不可用时不主动清空队列、删除缓存或重置歌曲位置。
- 当前音频流中断或签名播放 URL 过期时，仅向**原 `SourceProfile` 的同一个 `baseUrl`**重新解析该歌曲的播放资源地址，尽可能从原播放进度恢复；允许短暂重缓冲，不保证无缝。
- 无法恢复时保留队列与最近有效进度，提示具体原因并提供手动重试入口。
- `401/403`：在协议明确允许的情况下尝试刷新一次有效认证，未恢复则提示重新登录/无权限，不重复暴力重试。
- TLS 身份或证书校验错误、明显的认证拒绝、无效请求等，不作为无限重试条件；绝不自动改用其他地址或其他账号。
- 服务器失效、连不上网、缓存任务暂停等状态均可观察，但不承诺进程被强制终止后能够继续在线播放；进程重建后的队列/位置恢复按 F-001 要求设计。

**状态：用户已确认 S-004B-C。**

### 5.3 S-004C 已确认（方案 A）：服务器仅手动添加

- 本地音乐通过用户主动选择目录/设备授权获取，与服务器发现无关。
- Emby、Navidrome/OpenSubsonic 的服务 URL **只能由用户手动输入并确认保存**；第一版不包含 Emby UDP 广播、mDNS、SSDP、后台扫描或列表发现功能。
- 不自动补全 LAN/WAN 地址，不自动把发现候选合并为已有来源，不根据网络切换自动改写 URL（与 S-004A 一致）。
- 添加服务器仍需「测试连接」、认证与清晰的报错；用户提供的 URL 不代表其身份已被验证。
- 若今后支持扫描功能，应通过新的产品决策修订规格，不能偷偷作为首版功能加入。
- Android 17 / targetSdk 37+ 的 `ACCESS_LOCAL_NETWORK` 属于访问内网地址的系统权限问题，**即使不实现服务器发现，手动连接内网地址仍可能需要申请**；适当解释用途并在拒绝时提供提示。

**状态：用户已确认 S-004C-A。**

### 5.4 S-004D 已确认：HTTP/HTTPS、证书、反代与 VPN

**S-004D-H3 已确认：HTTP 与 HTTPS 默认允许。**

- 用户可直接在唯一 `baseUrl` 中输入 `http://` 或 `https://`，应用不会因 HTTP 要求单独确认，也不会擅自将 HTTP 变更为 HTTPS，或反向变更。此产品选择**不代表** HTTP 是安全的：明文 HTTP 可能泄露登录资料、Token、请求内容和音乐信息。应在连接详情显示清晰、非阻断的「未加密 HTTP」标记。
- 若输入 HTTPS，则必须校验证书链、主机名和有效期，绝不允许因失败自动改用 HTTP；TLS 出错不得用全局绕过校验处理。
- Android 的底层网络安全配置对明文流量有平台限制：由于来源地址由用户动态填写，可能需要在应用或构建级允许必要的明文连接，但应用层仍仅访问用户配置的地址；必须实测 Dart、libmpv、封面、歌词、音频缓存、HTTP Range 与重定向的行为。不能声称可以按 `SourceProfile` 动态改变系统级 Network Security Config。

**S-004D-T1 已确认：第一版仅使用平台可信证书并严格验证。**

- 不提供应用内上传/导入自定义 CA 与证书的功能；不提供忽略所有证书错误的开关。
- 用户在操作系统侧配置额外信任 CA，是否对 Flutter/Dart、libmpv 和平台网络栈都生效，要按平台实测，不能保证行为一致。
- 证书到期、域名不匹配、证书链不可信时提供可诊断提示，不记录明文认证资料。
- T2（应用内自定义 CA/证书）为未来候选，**不是**第一版已确认功能。

**S-004D-P 已确认：反向代理和安全重定向。**

- `baseUrl` 支持域名、端口及路径前缀，例如 `https://music.example.com/emby/`；API、歌词、封面及播放相对资源在相应路径下安全构建。
- 不自动推断、探测或改写反向代理后的真实内网地址，不擅自加入转发头。
- 不将凭证、Cookie、Bearer、Emby Token、Subsonic 认证参数、带凭据 URL 查询参数等转发到未经验证的不同协议/主机/端口。尤其拒绝把 HTTPS 身份资料静默降级到 HTTP。
- 对跨来源的重定向，先按请求目的与媒体鉴权模型进行隔离处理；独立签名媒体 URL 可以在无源站凭证转发的前提下经校验后使用。对 Dart 和 libmpv 的不同重定向行为都要测试。

**S-004D-V 已确认：VPN 视为普通网络。**

- 可以使用用户自行填写的 WireGuard/Tailscale/系统 VPN 可达 URL；不内置 VPN 管理、不扫描或猜测 IP、不智能切换地址。
- VPN 不构成关闭 HTTPS 校验的理由；VPN 中的 HTTP 仍是 HTTP，需显示普通明文连接标记。
- VPN 中断执行 S-004B 的有限网络重试和恢复，不能用另一个 SourceProfile 的地址替代当前 URL。

**S-004D-S 已确认：通用安全基线。**

- 各连接的凭证独立保存在平台安全存储，数据库使用不可直接解密的凭证引用；一台服务器的不同账号不共享会话或令牌。
- API、封面、歌词、音频流、Range、音频缓存等所有请求路径统一执行脱敏与可信重定向规则；日志不出现完整令牌、密码、认证查询参数或 Cookie。
- 更改地址要重新校验服务器身份和当前账号授权，不得将旧主机的凭证无条件发往新主机。
- 不支持自动服务器发现（S-004C），也不支持自动切换 LAN/WAN 双地址（S-004A）。

**决策状态：S-004D-H3/T1/P/V/S 均已确认。**

### 5.5 更新后的基础模型（S-004A 已确认原则，字段仍可调整）

```text
SourceProfile {
  id: SourceProfileId          // 同一服务器不同账号为不同 id
  type: emby | opensubsonic | local
  displayName: String
  baseUrl: Uri?                 // 远程来源：唯一手动管理地址；本地为 null
  credentialRef: SecureCredentialRef?
  verifiedServerId: String?    // 可取得时用于变更地址后的身份比对
  enabled: Boolean
  lastConnectivityStatus: ConnectivityStatus?
}
```

不再设计 `ConnectionEndpoint` 列表、`lan/wan` 地址角色或 `connectionMode=auto|lanOnly|wanOnly`。音乐与缓存索引以稳定资源身份作为基础，不以会过期的流媒体 URL 为唯一键。

## 6. 共同技术约束

- 音乐源协议适配与播放内核分离；增加来源无需重写播放服务。
- 音频缓存、歌单批量缓存任务与队列使用稳定资源身份，不以临时音频 URL 作为歌曲 ID。
- `baseUrl` 可由用户编辑，但不是 `SourceProfile` 身份；改址后必须先验证服务器与账号，防止将一个来源误映射到另一台服务器。
- 同一连接失败时绝不切到其他保存的 `SourceProfile`、猜测相似域名或修改 URL。恢复只能针对该连接及其被授权的资源。
- 网络故障恢复要保护原播放队列与位置，并对鉴权失效、证书错误、服务器宕机给出不同提示。
- Android 后台与 Windows 系统媒体控制必须进行真机/真实系统验收。
- S-006A 已确认跨源独立展示；S-006B/C 已确认收藏是本地特殊歌单，本地歌单可混合来源、云端歌单严格绑定一个来源；离线资源播放优先级仍待评审；云歌单多设备冲突遵循已确认 S-006E；S-005A/B 与 S-005C 数据规则保持有效。

## 7. S-004 更新后的验收场景（测试草案）

### 已确认决策的验收

1. 添加 Emby、Navidrome/OpenSubsonic，仅保存用户输入的唯一 URL；同类来源允许多个独立账户配置。

#### 8.2.2 已确认的触发原则与待实现细节

1. **首次连接（确认）**：账号认证通过后自动开始完整元数据索引；可见索引进度、取消/重试入口，不阻塞首页与已有数据的浏览。

3. **手动刷新**：无论何种模式都支持按来源及统一音乐库的刷新入口。单一来源刷新失败不影响其他来源；用户操作不会同时启动同一来源的重复同步任务。
4. **取消/断网/重启**：保留最近一次有效完整快照及同步进度；若协议支持可靠续扫，可从检查点继续，否则安全地重跑该轮；不把不完整快照作为删除依据。
5. **后台周期同步（确认不采用）**：第一版不主动安排按时触发的后台音乐库扫描。已开始的同步可依平台进程生命周期继续或中断并在下次启动恢复；不得借用或长期维持音频前台服务来执行元数据扫描。
6. **媒体库索引 vs. 音频缓存**：周期性或启动同步默认只拉元数据，不偷偷缓存全库音频、专辑原图或歌词正文。
7. **网络限制**：同步失败时按 S-004B 进行有限重试，不无限轮询；仅 Wi-Fi 刷新等设置不是首版已确认功能。
8. **同步公平性**：每个 `SourceProfile` 有独立状态和最后成功时间；实施时限制并行数并为当前音乐播放、歌词和封面加载留出网络优先级。

#### 8.2.3 技术可行性核验

- Android 的 WorkManager 适合可延后、需要可靠调度的数据同步；周期任务有最短重复间隔且**不保证准点执行**，受网络、功耗和设备约束。第一版不应把“Android 播放媒体前台服务”误用为长期元数据扫描的理由。
- Flutter 社区 `workmanager` 的 Android 能力成熟度与桌面支持范围并不完全一致。其 Linux 计划任务能力仍标记实验性，Windows 没有同等通用保证；C 方案必须明确平台差异。
- 本地文件变化的提醒可用 MediaStore/文件系统监听辅助触发，但不能依赖监听作为全部差异的唯一事实来源。

### 8.3 不同协议的同步能力（实现候选，非已确认）

### 8.4 正确性与安全性（推荐为后续强制基线）

- 只索引该连接账号**实际有权看到的内容**；每条记录始终携带 `sourceProfileId` 与远程项目 ID；本地设备文件作为独立来源，不能与服务器记录直接合并为同一个原始音频资源。
- 写入使用分页事务 / 快照代次：只有本次完整同步成功后才能据「本次未出现」判断远程记录被删除或暂不可见；同步中断不得误删除历史索引。
- 源被停用、断线、登出、删除、权限缩小、服务器改址，以及用户主动发起的歌单缓存任务及其完整文件的保留/清理策略 **须后续单独评审**；特别不能把“音乐库列表里不存在”直接等同于“可删除已完成的缓存”。

### 8.6 S-005C 已确认：资源缺失软删除 + 删除来源时清理本地数据

> **已确认决策**：S-005C1 = B；S-005C2 = A。注意二者适用的操作完全不同：**远端同步未找到歌曲 ≠ 用户主动删除来源**。只有后者在用户明确确认后允许清理来源的本地数据。

#### 8.6.1 S-005C1 = B：远端删除/权限变化采用软删除

- 只在一次**完整且可信的来源同步**成功后，或获得明确、可归属当前账号的条目查询结果时，才把缺失条目标记为 `Unavailable`；服务器断网、401/403、认证失效、分页中断、取消扫描或进程退出，均不可直接推导远端删除。
- `Unavailable` 的意思是「当前账号下已确认无法正常访问」，**不等于已证明远端物理文件被删除**。统一音乐库和默认搜索结果隐藏此记录；数据库保留来源身份、最低限度的元数据与墓碑记录。
- 保留这些记录在**本地收藏、用户创建的歌单、播放历史、已保存的播放队列中的引用**。之后同一 `TrackRef` 恢复可访问时，重新启用原有引用，不自动重复添加。
- 远端单曲变为不可用时，**不自动删除已经完成且校验通过的缓存歌曲**。已缓存歌曲的离线播放资格和账号权限遵守后续离线及授权专项；不得尝试用其他账号越权取得失效来源的资源。
- 本地用户授权目录或可移除磁盘暂时无法访问时，同样不能直接级联删除个人记录；采取待验证/不可用状态并待再次扫描。

建议状态枚举：`Available`（可访问）、`Unverified`（暂时无法确认）、`Unavailable`（完整同步后当前账号不可见）、`SourceDisabled`（用户停用来源）。`Unverified` 不能与 `Unavailable` 混用。

#### 8.6.2 S-005C2 = A：停用保留；删除来源确认后一并清理来源本地数据

- **停用来源**：保留配置、凭证、音乐库元数据、音频缓存及个人引用，停止自动同步和该来源的在线请求，默认从统一音乐库/搜索隐藏。重新启用时重新验证认证并同步。停用**不能**触发磁盘文件删除。
- **删除来源**：必须先展示影响范围并进行明确确认；确认后移除该 `SourceProfile` 的连接配置、认证凭证、索引、来源专属收藏/歌单关联及播放历史、由应用管理的完整歌曲缓存与歌单批量缓存任务（含应用管理的歌词、封面缓存），并释放相应空间。不提供「删除连接但保留来源本地数据」作为首版内置选项。
- 对其他 `SourceProfile`（包括同一服务器不同账号）的数据、凭据、缓存文件绝不进行连带删除。物理磁盘块如被多个来源合法共享，必须有明确的所有权/引用计数，不能误删其他仍在使用的资产。
- **绝不删除用户自己磁盘或设备中的原始音乐文件**：对本地音乐来源而言，「清理来源本地数据」只清理本应用的索引、缓存、托管副本、个人关联和授权记录，不递归删除原始本地目录或媒体库文件。
- 来源关联播放条目正被使用时，先取消/结束相关缓存和网络操作，解除活动播放引用，再清理；混合跨源列表中不受影响的其它来源内容必须保留。关联条目在收藏/歌单中的清理粒度与列表语义将在 S-006 定案，但不能产生指向已清理来源的悬挂可播放引用。
- 只清理**本机应用数据**，不得因删除 SourceProfile 而向 Emby / Navidrome API 发送服务器侧删除歌曲、清空歌单或取消收藏命令。
- 对本地缓存与批量缓存任务执行原子性清理计划：先阻止新请求并记录操作，再清理数据库与文件；崩溃重启后能继续收尾。清理完成前不得宣称已删除成功。

**确认界面建议（文案后续 UI 评审）**：显示来源名称、所含歌曲索引数、应用管理完整歌曲缓存的大致空间占用、将影响的本地关联记录，并突出提示「用户设备上的原始本地音乐文件不会被删除」。

### 9.1 基础身份与跨源边界（依据 S-002、S-003、S-005C、S-006A）

- `TrackRef = (sourceProfileId, remoteTrackId)`：每条歌曲始终引用具体来源账号；本地文件为设备自己的来源。不同账号/来源不可仅凭曲名、歌手等字段判断等价。
- S-006A：同名/同曲跨来源仍分别展示；不自动替换云歌单、播放队列和缓存中的来源。
- 同一台 Emby 的两个账户是两个不同 `SourceProfile`；云端歌单只能引用创建时选定的 **同一个 SourceProfile** 的曲目。跨服务器或跨账号添加均不允许。
- **停用来源**保留本地歌单引用、收藏、云歌单镜像及同步状态；来源恢复可继续访问。**服务器软删除曲目**只标记不可用，保留收藏/歌单中的引用，且不自动删除完整歌曲缓存（S-005C1）。
- **用户明确删除来源**时遵守 S-005C2-A：确认后清除其本机音乐库索引、完整歌曲缓存、批量缓存任务和相关歌单镜像，并移除本地混合歌单/收藏里属于该来源的条目；其他来源条目保留。只清理本机数据，**不得因删除连接而请求远端删除歌单、取消收藏或删除音乐文件**。

### 9.2 S-006B 已确认：收藏本质为特殊本地歌单

- 用户点击应用内爱心 = 将该 `TrackRef` 加入/移出当前设备的系统级“我的收藏”本地歌单。允许 Emby、Navidrome、设备本地音乐混合收藏。
- 收藏是**当前设备本地数据**，不自动写回 Emby 或 Navidrome 的远端星标/收藏 API；同一账号在 Android 和 Windows 上的收藏不因同源登录而自动保持一致。未来若需跨设备应用级同步，应另行设计。
- 收藏可复用普通本地歌单条目存储、顺序和软删除关联；对用户表现为固定的特殊歌单/入口，而不是必须另外维护一个不兼容的数据集合。
- 产品实现建议（未单独确认）：固定收藏歌单不能被整体删除或重命名，爱心切换会追加/移除具体歌曲；如允许重复收藏，需另行定义，但通常爱心语义建议单曲只有一个收藏条目。
- 服务器原生的星标/收藏能力不等价于本机收藏；首版爱心行为不调用 `star/unstar` 或 Emby 收藏写入接口。是否独立读取/展示服务器星标，留待将来评审。

### 9.3 S-006C 已确认：普通歌单仅分本地与云端两类

| 歌单类型 | 数据归属 | 可添加曲目 | 修改/同步 | 用途 |
| --- | --- | --- | --- | --- |
| 本地歌单 `local` | 当前设备应用数据库 | 任意已配置来源（包括本地文件）的曲目；可混合 | 在本设备编辑，不自动写回远端 | 个人混合音乐列表 |
| 云端歌单 `cloud` | 某一远程来源的服务器；本地留镜像/同步状态 | **仅创建时指定的 `sourceProfileId`** 中的曲目 | 从远端读取，并把被允许的编辑写回同一远端（双向同步） | 与同一账号的其他客户端共用服务器歌单 |

- **新建本地歌单**：在本机创建，来源不限，允许混合 Emby + Navidrome + 本地曲目。
- **新建云端歌单**：用户必须选择一个有歌单写入能力且已认证的远端 `SourceProfile`；调用对应 Emby/OpenSubsonic API 新建，成功后持有 `remotePlaylistId`。本地来源没有云端歌单服务器，不作为目标。
- 云端歌单建立后**来源不可随意更改**。任何添加歌曲操作都要校验 `trackRef.sourceProfileId == playlist.sourceProfileId`；UI 和数据层均校验。
- 云端歌单是服务器实体的本地镜像，而不是修改后与服务器脱节的普通本地歌单；服务端创建/添加/删除/重排/改名等操作需进行协议、权限与歌单可编辑能力检测。
- 从服务器同步歌单应保留曲目顺序以及必要的条目级远端 ID（例如 Emby 的 `PlaylistItemId`、OpenSubsonic 的索引），不能仅用歌曲 ID 作为歌单行唯一主键。
- 云歌单远端内容更新和新建/编辑确认都需要同步：S-005B 不进行后台**周期性全库扫描**，不妨碍在用户进入云歌单或修改云歌单时执行必要网络操作；自动刷新频率、网络重试和并发仍遵守既有来源规则。

### 9.4 S-006C 已确认：转换仅通过“复制副本”，不移动原歌单

**云端 → 本地**

1. 读取该云端歌单可访问的条目及顺序（离线时可依据已同步快照，需标示快照状态）。
2. 生成一个新的 `local` 歌单 ID，逐项复制原歌曲 `TrackRef` 和排序；副本允许后续添加其他来源。
3. 后续本地副本的编辑不影响原云歌单，云端变动也不自动修改副本。

**本地 → 云端**

1. 用户选择一个具体远端 `SourceProfile`（例如“家庭 Emby · 用户甲”，而不是笼统的 Emby 协议类型）。
2. 只筛选本地歌单中 `sourceProfileId` 与目标**完全一致**的歌曲，保留其出现顺序；其他来源的条目**不自动匹配、重定向或替代**。
3. 创建目标来源上的新云歌单，并写入符合该来源且当前有权限使用的条目；生成独立本地镜像。
4. 原本地歌单完整保留。转换前建议预览“符合条件的条目数、跳过的不同来源条目数、因权限/已失效跳过的条目数”，避免误解。
5. 若服务器拒绝写入、网络失败或仅部分成功，要明确报告实际创建/写入状态，避免形成用户以为成功的幽灵歌单；后续幂等/补偿策略另行评审。

“复制”是快照行为而非持续关联：两个副本在复制后彼此独立；重复歌曲是否允许多个条目与空结果如何处理仍属实现/UI 待评审，不改变独立副本原则。

### 9.5 已核对的服务器能力与边界

- Emby 官方 API 支持歌单创建、列出条目、添加和移除条目；移除必须正确使用歌单条目 ID（`PlaylistItemId`）而不是直接拿歌曲 ID。部分版本还提供条目移动接口。
  - https://dev.emby.media/doc/restapi/Playlists.html
  - https://dev.emby.media/reference/RestAPI/PlaylistService.html
- OpenSubsonic/Subsonic 提供 `getPlaylists`、`getPlaylist`、`createPlaylist`、`updatePlaylist`、`deletePlaylist`。`updatePlaylist` 对添加和删除的参数语义不同于 Emby，删除依据条目位置。客户端应为不同协议提供独立的歌单操作适配器。
  - https://opensubsonic.netlify.app/docs/endpoints/createplaylist/
  - https://opensubsonic.netlify.app/docs/endpoints/updateplaylist/
- Navidrome 实现了上述 Subsonic 歌单端点，但智能歌单以及启用了自动导入的部分 M3U 歌单**曲目列表是只读**：用户定义的“云歌单双向同步”是对于服务器权限和歌单类型允许编辑的普通歌单成立；只读歌单仍可浏览与“复制为本地”。不可向服务器假报写入成功。
  - https://www.navidrome.org/docs/usage/smartplaylists/
  - https://navidrome.org/docs/faq/

### 9.6 数据模型建议（实现提案；字段尚未定案）

```text
Playlist {
  id: LocalPlaylistId               // 客户端稳定 ID
  type: local | cloud                // 我的收藏存为 local + systemRole
  systemRole: favorites | none
  displayName: String
  sourceProfileId: SourceProfileId?  // cloud 必须有；local 必须为 null
  remotePlaylistId: String?         // cloud 创建成功后必有
  remoteRevision: String?           // 有可靠版本标识时采用
  syncStatus: synced | dirty | conflict | error | readOnly
  lastSyncedAt: Timestamp?
}
PlaylistEntry {
  entryId: LocalEntryId              // 独立歌单条目身份
  playlistId: LocalPlaylistId
  trackRef: TrackRef
  orderIndex: Integer
  remoteEntryId: String?            // Emby 等提供时记录
  titleSnapshot: String?            // 歌曲软删除后仍可显示
}
```

硬约束：本地歌单 `sourceProfileId=null` 允许混合；云端歌单 `sourceProfileId` 必填且所有 `PlaylistEntry.trackRef.sourceProfileId` 必须与之相同。“我的收藏”是预创建的 `local` 歌单，不另建第二套收藏真相表。

### 9.7 S-006B/C 功能验收（依据已确认原则）

1. Emby A 与 Navidrome B 的同名歌曲独立展示，加入“我的收藏”后只收藏被点击的具体 TrackRef。
2. 本地混合歌单可以包含 Emby A、Navidrome B 和本地文件，排序和编辑仅影响本设备。
3. 从本地混合歌单复制到 Emby A 云歌单后，目标仅有来自 Emby A **这个账号配置**的曲目，顺序保留，原本地歌单不变。
4. 从 Navidrome B 云歌单复制为本地歌单后，可在副本添加 Emby A 的歌曲，原云歌单不变。
5. 两台设备使用同一个远端账号读取同一云歌单时，应该能看到服务器成功提交并可访问的变更；不同账号的同一服务器连接不会串歌单权限。
6. 云端只读/无权修改的歌单不允许声称写回成功，但可以复制为本地歌单。
7. 仅服务器歌曲软删除时保留本地/云端镜像引用并标记不可用；用户删除来源并确认时，清理本机相关引用和镜像，不能因删除来源向远端发送 `deletePlaylist`。
8. 首版爱心不修改 Emby/ Navidrome 原生星标状态，Windows/Android 的本地收藏互不自动同步。

### 9.8 S-006D 已确认（方案 B）：云歌单支持离线编辑，联网后同步

**用户已确认的产品语义**：

- 云歌单在无网络时仍可对本机最近一次已同步的镜像进行**添加、移除、重排、改名**等服务器允许的操作；交互即时生效，UI 明示「待同步」。若已知目标歌单只读，不提供不能写入的编辑操作。
- 本机的离线修改必须持久化于 SQLite / 应用数据库，不以进程内列表或临时内存存放；应用重启后仍保留待同步变更。
- 恢复可访问的网络和有效登录后，尝试把待同步变更发送到该云歌单所属的**同一个 `sourceProfileId`**，不切换到其他服务器账号，也不跨来源迁移。
- 离线修改不会在“编辑成功”时假称“已写入服务器”；必须区分本地保存成功与远端确认成功。该选择并不要求应用被系统杀死时仍可在后台持续同步。
- 本地收藏依然是特殊**本地歌单**，与云歌单待同步队列分开；本地→云端、云端→本地仍只通过**复制副本**，不改变既有转换原则。

**支撑此决定的实现基线（实现提案；冲突解决遵循已确认 S-006E-D）**：

1. 本地编辑歌单镜像和记录待提交操作应发生在**同一个数据库事务**中，确保崩溃时不会丢失用户操作；所有变更带有 `operationId`、`playlistId`、`sourceProfileId`、`baseSnapshotId`、本地顺序号及状态。
2. 为每个云歌单创建有序的 `PendingPlaylistOperation` 队列，按歌单串行提交，允许不同歌单各自同步；操作类型包含添加条目、移除**指定条目实例**、重排、改名。涉及重复歌曲时不能仅用 trackId 识别条目。
3. 同步前先读取服务器当前歌单并检查权限、远端条目列表与上次同步基线是否相容；如果服务器无可靠修订号，可依据服务器返回的条目顺序、远端条目 ID、名称等计算客户端快照指纹。指纹只帮助判断差异，不能冒充服务端并发锁。
4. 在远端快照未变化、操作仍适用时按顺序提交，并读取服务器最新状态验证结果。收到超时但不知服务器是否已成功执行时，先重新读取远端再判断，**不能盲目重复**可能导致重复添加或错删的请求。
5. 如果发现服务器上有其他设备的并发修改、目标条目已消失、服务器拒绝编辑或账号权限变化：停止可能破坏远端数据的后续写入，保留本地修改和可诊断状态，进入 S-006E 规定的冲突流程；绝不默默丢弃用户更改。
6. 只有获得远端成功确认并更新本地镜像后，才能清除对应待提交操作；服务器返回只读或不支持的歌单应停止写回，并允许用户复制为本地歌单。
7. 与 S-005B 一致，不启用周期后台音乐库扫描。云歌单同步可由用户编辑时（在线）、应用回到前台、网络恢复且应用仍运行时、进入歌单页面或手动点“同步”触发。**不承诺应用完全退出后由后台定期同步**。

**推荐的数据结构扩展（实现提案，字段不做永久锁定）**：

```text
PendingPlaylistOperation {
  operationId: UUID
  playlistId: LocalPlaylistId
  sourceProfileId: SourceProfileId
  kind: addEntry | removeEntry | moveEntry | rename
  payload: StructuredOperationPayload
  baseSnapshotId: String?
  sequence: Long                   // 单歌单单调顺序
  state: queued | sending | uncertain | conflict | failed
  createdAt: Timestamp
}
CloudPlaylistSyncState {
  playlistId: LocalPlaylistId
  lastRemoteSnapshot: PlaylistSnapshot?
  remoteRevision: String?          // 若协议提供可信修订标识
  lastSyncAt: Timestamp?
  status: synced | pending | syncing | conflict | readOnly | error
}
```

**本轮新增验收场景**：

- Android 断网后对云歌单添加、删除、排序，退出并重新打开应用，所有本地修改和待同步队列仍然存在。
- 重新联网后，同一歌单的修改按顺序提交，只向其归属的 Emby / Navidrome 账号写入；成功确认后状态变为已同步。
- 提交添加歌曲请求后连接中断，即使结果未知，也不会盲目重发导致歌曲重复。
- 服务器权限收回或歌单变为只读，离线操作不得被静默丢弃，也不能假报同步成功。
- S-005C2 已确认的“删除来源并清理本地相关数据”仍有效：删除来源时应提示有多少未同步云歌单修改将一并丢失；经用户明确确认后才清理本地队列。绝不因为删除本地来源向远端删除歌单。

### 9.9 S-006E 已确认（方案 D）：安全合并、冲突暂停、保留本地修改

**产品决策（已确认）：**

- 当本地有未同步云歌单更改，而远端版本也变化时，先比较「上次确认同步基线」（Base）、当前远端快照（Remote）和本地待同步后的目标状态（Local）。只自动合并**能够可靠判定不冲突、且服务端支持正确表达**的操作。
- 如果同一条目遭遇不兼容的增删、多个客户端同时改变重排位置、歌单已经被服务器删除，或服务端缺乏足够信息判定安全，则**暂停该歌单后续写回**，提示用户选择处理方式；其他歌单仍可继续同步。
- **绝不静默覆盖远端修改、丢弃本地离线更改或将冲突显示为已同步**。本地待同步操作与同步前镜像继续持久化，允许用户将当前本地状态「复制为本地歌单」进行保全。
- 解决冲突后，必须以用户确认的合并/选定结果重新生成待提交操作，并重新读取服务器以确认可应用的前提。不能直接重放原有已过期的位置索引。
- 若协议没有可靠服务器修订号，客户端保存的名称与条目序列指纹只能作为变化检测辅助，**不是原子并发控制**；即使比较通过，也存在检查之后、提交之前的竞争窗口。写入后要重新读取结果，异常则保留状态并提示人工检查。

**建议的合并判定（实施细则，仍需要真实服务器集成测试）：**

| 情况 | 默认处理 |
| --- | --- |
| 远端没有变化，本地操作仍有合法目标 | 按顺序提交、读取验证 |
| 两端向不同位置独立新增歌曲，能够可靠确定顺序 | 可自动合并，提交后回读 |
| 两端都更改了同一首重复出现的歌曲条目 | 以条目实例 ID/快照为准；无法确认则冲突 |
| 两端对同一区段重新排序 | 暂停写回，用户决定 |
| 一端删除歌单，一端修改该歌单 | 暂停写回，转入 S-006F 删除冲突专项 |
| 上传超时，不能确定服务器是否已执行 | 状态标记 `uncertain`，先读取服务器再决定是否继续；**禁止盲目重发** |

**推荐存储**：`PlaylistSnapshot(baseSnapshotId, entries, name, fetchedAt, remoteRevision?)` + `PendingPlaylistOperation(operationId, baseSnapshotId, sequence, state, ...)` + 本地用户可见编辑结果。待提交操作与 UI 状态应在同一事务中持久化。

**已确认验收**：Android 离线添加 D，Windows 在线添加 E，重连后只在可靠保留双方操作时自动合并；Android 离线重排且 Windows 同时重排，必须停在冲突态并保留本地变更；进程重新启动后仍能查看冲突内容、生成本地副本并解决。

### 9.10 S-006F 已确认：云歌单删除、权限变化与同步失败

#### 9.10.1 S-006F1 已确认（方案 A）：云歌单仅在线执行服务器删除

- 删除整张云歌单的远端操作**只能在当前来源在线、已认证且服务器明确支持安全删除歌单容器**时启动；离线时此操作不可提交，也不创建待删除队列。在线前需明确二次确认歌单名称、绑定的 `sourceProfileId` 与远端对象。
- 当前云歌单存在未同步修改或冲突时，必须先提示并解决/保全草稿，不能直接丢弃未同步更改再删除。
- OpenSubsonic 使用专用 `deletePlaylist` 端点；Emby 的通用 `/Items` 删除具有删除媒体文件风险，**严禁未经验证地将其映射为歌单删除**。无法确认安全行为的服务器或版本不启用此功能。
- 删除整张云歌单、从歌单移除一个条目，以及删除本机音乐源（S-005C2-A）是三种不同操作。删除本机来源只清理本机应用管理数据，**绝不**要求服务器删除歌单或原始音频。
- 删除请求返回结果不明时，先回读确认远端是否仍存在，再给出错误状态；不能以超时代表“已删除”。
- 「从本设备移除云歌单但服务器不删除」的独立入口**并非本轮已确认的必需功能**，不把曾建议的 F1-C 误记为已通过。

#### 9.10.2 S-006F2 已确认（方案 A）：权限控制与草稿保全

- 对每个远端歌单保留功能级能力：`canRename / canAddEntries / canRemoveEntries / canReorder / canDeletePlaylist`。服务端返回的只读字段只作为参考，实际服务器权限检查具有最终效力。
- 对**已明确无权限**的动作立即禁用继续编辑与写回；对于服务器后来收回的权限，暂停该类待同步操作并持久化所有未同步修改与基线快照，不能假报成功。
- 提供「复制当前本地草稿为本地歌单」以保全编辑内容；这个复制操作不修改服务器上的只读歌单，也不清空原待同步队列。
- 当权限恢复后，可由用户重新尝试同步；先再次读取远端、检查 S-006E 合并冲突，而不是机械重放过期位置索引。
- 即使部分操作不可用，其他获准的操作可依赖服务器能力独立处理，但不能因此破坏仍在等待的离线修改。

#### 9.10.3 S-006F3 已确认（方案 B）：有限自动重试 + 手动重试

- 仅对可恢复的网络错误、暂时性 `5xx`、可等待的 `429` 等执行有限退避重试，遵从 `Retry-After`（如有）。具体重试次数、退避窗口和超时为测试参数，不在产品层硬编码。
- `401` 先走原账号合法刷新/重新登录；`403`、只读和权限变更暂停写回；远端歌单 `404` 进入冲突处理，不换账号或自动在服务器创建替代歌单。
- 写请求超时、连接中断后结果未知时，先回读远端并对照同步基线，**禁止盲目重发可能重复添加、错删或错序的非幂等操作**。
- 自动重试耗尽、协议明确拒绝、或远端修改与本地更改无法安全合并时，保留持久化操作队列并提供手动重试/冲突处理入口。
- 可在用户编辑（应用在线）、回到前台、打开歌单、网络恢复且应用仍运行时尝试同步；不启用后台周期扫描，也不承诺应用完全退出后继续周期同步（与 S-005B 一致）。

#### 9.10.4 S-006F 验收标准（依据已确认方案）

1. 离线时服务器云歌单的「删除整张歌单」操作不可提交；离线编辑歌单条目仍遵循 S-006D。
2. 在线删除要二次确认并进行远端权限与端点检查。Emby 删除操作不可误删媒体库源文件。
3. 只读权限变化后，未同步条目、顺序、名称和操作队列仍在；用户可复制独立的本地草稿。
4. 网络 `5xx`、`429`、短暂断连按有限重试处理；`403` 不反复重试；超时结果不明先远端回读。
5. 所有未确认成功的操作在设备重启后仍能追踪状态并手动恢复；冲突态不会假装同步完成。

## 10. S-007 播放队列、播放模式与播放状态持久化（S-007A/B/C/D 均已确认）

> **S-007A/B/C/D 已全部确认**。真正重启后恢复但默认暂停；尚存活的后台播放会话在 UI 重建时直接重连。技术路线倾向 Flutter + media_kit + 平台媒体服务，尚待架构专项定案。

### 10.1 队列核心原则（含 S-007A 已确认规则和实现建议）

- **歌单（Playlist）是持久的用户集合**，可能是本地或云端；**队列（PlaybackQueue）是当前设备的临时播放会话**。播放操作不应默认修改原歌单或触发云歌单同步。
- 播放队列允许混合来自 Emby、Navidrome 和本地音乐的曲目，但每个条目必须保留 `(sourceProfileId, remoteTrackId)`，不做跨来源智能替换。
- 队列条目使用独立 `queueEntryId`，同一 `TrackRef` 允许重复出现；当前播放位置引用队列条目而非单纯的 `trackId`。
- 应用队列控制器负责播放逻辑；**正在运行的会话是当前播放状态的实时权威**，本地数据库保存可恢复的持久化快照。重建 UI 时不得使用旧快照覆盖活跃会话。临时签名 URL、Token、播放器内部句柄不得持久化为队列身份。
- Android 的后台媒体会话可在界面销毁后维持运行，但被系统终止/强行停止时并无无条件播放保证；队列持久化负责重新启动后的恢复。Windows、Linux 与 Android **已确认各自保存独立播放状态**，不云同步队列与播放进度（S-007C2-A）。
- 推荐抽象 `QueueController -> PlaybackCoordinator -> PlaybackEngine(media_kit)`，统一 UI、Android 系统控制、Windows SMTC、Linux MPRIS 对队列发出的操作；避免各入口各自直接修改播放器列表。

### 10.2 S-007A 已确认（方案 A）：队列是独立快照

**用户已确认：**

- 从任意来源的专辑、歌单或搜索列表开始播放时，创建一份独立的播放队列快照。队列中的条目保留创建时的顺序与 `TrackRef`；正在播放后，原歌单变化**不会**自动增删、重排或替换当前队列。
- 队列中的「下一首播放」「添加到队列」「移除」「手动排序」「清空」只影响当前播放会话，**不修改原始本地歌单、云端歌单，也不产生服务器歌单写入操作**。
- 队列允许跨来源条目与同一 `TrackRef` 多次出现；每一条有独立 `queueEntryId`。队列引用原资源，不另造跨来源的曲目标识。
- 若队列来自云歌单，云歌单离线编辑与多设备同步冲突机制仍独立运行（S-006D/E/F），不会隐式修改正在播放的快照。
- 队列可记录 `originPlaylistRef` 以供界面导航，但这**不意味着**保持实时联动；首版不默认增加“从原歌单刷新当前队列”的快捷操作。
- 音源断网/失效时，队列快照仍需遵循 S-004B 的恢复约束与 S-005C 的软删除引用规则；播放失败的自动跳过方案在 S-007D 再确认。

**验收基线**：从 Emby 云歌单 A→B→C 开始，插入 Navidrome 的 X 为下一首，队列可以变为 A→X→B→C；Emby 原歌单顺序保持 A→B→C。其他设备修改原云歌单后，当前队列仍保持用户本机操作后的内容。

### 10.3 S-007B 已确认：顺序、循环、随机与上一首行为

**用户确认：**顺序到尾停止、列表循环、单曲自然结束重复但手动切歌生效、随机遍历顺序持久化、随机与循环可组合、上一首按实际播放历史回退；**无论播放了多少秒，按上一首都要切曲，绝不按 3/5 秒阈值重播当前曲目**。

#### 10.3.1 模式模型和自然播放结束行为（已确认）

- 使用两个相互独立的状态：`repeatMode = off | single | all` 与 `shuffleEnabled = true | false`。随机与列表循环、单曲循环允许组合。
- 顺序且非循环：依队列排序播放；队列最后一条**自然结束**时停止自动推进，队列保留。
- 列表循环：非随机时尾部自然结束回到首条；随机时每轮按保存的随机顺序依次播放每个队列条目，轮末生成并保存下一轮排列。
- 单曲循环：当前 `queueEntryId` **自然播放结束**才重播；用户主动点下一首/上一首必须切换曲目，不得被单曲循环锁住。
- 随机播放：使用**持久化的无重复队列条目排列**逐首推进，不能每按一次下一首就重新随机抽取。一个 `TrackRef` 在队列出现两次时，因 `queueEntryId` 不同，仍是两次独立播放机会。
- 自然结束、用户主动跳过与播放器报错分别处理。错误重试及自动跳过留在 S-007D 评审。
- 单条队列：顺序模式自然结束后停止；列表循环和单曲循环可持续重复。空队列时导航命令无效。

#### 10.3.2 随机队列、插播和历史（已确认）

- 开启随机后，当前歌曲保持不变，对后续尚未访问的队列条目生成本轮顺序。实际顺序、当前游标、历史记录都必须持久化。
- 新一轮随机仅在启用 `repeat=all` 且本轮完成时生成；`repeat=off` 遍历结束停止。
- 关闭随机时按照用户原始队列排序继续，保持当前条目，不清空原队列与历史。
- 「下一首播放」优先进入紧接当前曲目的待播放位置，不能被随机队列推迟；添加、移除、调整条目要同步更新未播放区段及游标，不重排已访问历史。
- 用户从上一首返回后再次点下一首，优先沿既有真实访问记录前进；避免生成随机新分支。
- 与 S-007A 一致，以上操作只修改当前队列，**不写回来源歌单**。

#### 10.3.3 上一首按钮（已确认：始终切歌）

- **已确认取消 3 秒/5 秒阈值**：点击上一首，无论当前播放位置是 1 秒、20 秒还是歌曲末尾，始终执行「导航到上一条曲目」指令，不通过上一首重播当前曲目。
- 优先查找最近实际播放过的**上一条 `queueEntryId`**；随机模式也使用真实历史，不临时抽取另一曲。
- 对应历史尚未建立时，若当前队列播放序列存在确切的前驱条目，可导航到它；若确实没有前驱目标，命令不应假装切换成功，也不应悄悄从 0 秒重播当前歌曲。
- **尚待边界细化**：在「列表循环的第一曲且没有访问历史」时上一首是否回绕到最后一曲；随机播放历史为空时的具体边界。用户尚未专门确认该边界，实施前以明确测试用例裁定。
- 点击上一首属于切曲指令，和进度条 Seek、暂停后继续播放严格区分。UI、蓝牙按键、Android 系统控制、Windows SMTC、Linux MPRIS 均通过同一队列控制器执行。

#### 10.3.4 播放内核边界（已确认行为的实现要求）

- `media_kit` 提供 `PlaylistMode.none/single/loop`、`setShuffle` 等 API，但官方文档指出 `Player.open()` 会重置 Shuffle。**播放顺序及历史不能只保存在播放器内核中。**
- 推荐应用层的 `QueueController` 作为顺序、历史、循环和快照队列的权威状态源，`media_kit` 用于实际音频播放；仍需在技术架构评审中决定是否由应用层完全调度引擎列表。
- 上述已确认行为须覆盖 Android 系统媒体控制、Windows SMTC 和 Linux MPRIS，一端行为不能与另一端产生不同语义。
- 参考：https://pub.dev/documentation/media_kit/latest/

### 10.4 S-007C 已确认：重启后恢复暂停、不同设备独立

**S-007C1 已确认（方案 A）；S-007C2 已确认（方案 A）。** 应用 UI 生命周期与真正的播放器进程/会话生命周期必须区分，不能因页面重新打开而覆盖后台正在播放的内容。

#### 10.4.1 S-007C1-A：后台会话活跃时直接重连；真正重启后恢复且暂停

- **仍存活的会话**：Android Activity 重建、通知栏切回 UI、Windows/Linux 托盘重新打开窗口，都必须连接已有播放器会话，保留正在播放、暂停、进度、队列与音频输出状态；禁止重新加载过期磁盘快照造成双播放器实例或暂停。
- **会话真正终止后的新进程启动**：从设备自己的持久化快照恢复完整队列、当前 `queueEntryId`、最近有效位置、循环与随机模式、实际播放历史及队列排序，**默认暂停，不自动发声**。
- 用户明确点按播放，或通过蓝牙耳机/通知栏/系统媒体键发出播放命令，属于主动播放指令：允许从恢复的会话继续播放，不受“被动启动默认暂停”限制。
- 重新播放前根据 `TrackRef` 解析当前合法本地文件/远端 URL，不能依赖持久化的签名 URL 或旧 Token；来源失效按照已确认 S-007D 错误策略处理。
- 从播放器异常退出后的快照恢复**不等于**保证精确到毫秒；位置保存节流及安全检查见下文实现建议。

#### 10.4.2 S-007C2-A：Android/Windows/Linux 各自保存自己的播放会话

- Android、Windows、Linux 分别保存播放队列、队列编辑、当前条目、位置、随机排列、真实播放历史与循环模式，**不自动同步播放状态**。
- 即使三台设备连接的是同一个 Emby/Navidrome 账号，也不得将另一设备的队列和进度写入本机；不构建本版跨设备“接力播放”。
- 与此独立：S-006 已确认的**云歌单双向同步**仍照常运行；共享云歌单不是共享正在播放的设备会话。
- 设备本地的来源 `SourceProfileId`、本地文件路径和快照主键不能假设跨设备相同。

#### 10.4.3 状态持久化时机（实现建议；未锁定时间参数）

- 必须持久化：队列条目顺序、各条 `queueEntryId`、当前条目、播放进度、`repeatMode`、`shuffleEnabled`、本轮随机序列、访问历史/历史游标、暂停与停止状态、快照版本及时间戳。
- 队列增删/排序、切歌、模式切换、暂停、停止及正常退出时及时事务保存；播放中定期节流保存位置，建议先用 5～10 秒检查点测试，最终频率依据功耗和崩溃恢复表现决定。不能将该数字理解为用户已确认的固定阈值。
- 突然断电、系统终止时，最多可能丢失最近一次位置快照后的进度，不承诺完全无损；但不能无故清空已成功落盘的队列。
- 可缓存稳定曲目引用与必要的显示快照，不能把签名媒体 URL、访问令牌和媒体内核句柄持久化为队列身份。
- 最近位置接近歌曲末尾、队列含不可用资源、离线数据缺失等场景由播放与缓存专项进行兼容验证。

#### 10.4.4 S-007C 验收基线（已确认）

1. Android 正在播放时反复切换后台、锁屏、重建 Activity，回到 UI 后仍是同一正在播放的会话，没有重复出声、跳进度或被强制暂停。
2. Windows/Linux 将窗口关闭到托盘后再次打开，播放器实例继续运行；真正退出应用再启动时恢复原队列和位置，但保持暂停。
3. Android 进程真正退出后重新启动，恢复当前条目、进度、模式、随机历史与队列，**不主动播放**；用户按播放后才输出音频。
4. 系统蓝牙/通知栏/媒体键明确发送“播放”命令时，允许主动恢复当前会话；不是因打开 App 而自动续播。
5. Android 与 Windows 同时使用同一服务器账号，播放不同歌曲互不覆盖；云歌单依旧能够正常同步。
6. 崩溃或强行终止后恢复不超过已测试进度检查点误差，队列及已落盘编辑保持一致。

### 10.5 S-007D 已确认：播放错误、不可用歌曲、连续失败与跳过

> **已确认：D1 采用方案 B，D2 上限为连续 3 条不同队列曲目。** 仍遵守 S-004B 有限重试与同源恢复、S-005C 软删除、S-007A 独立队列、S-007B 播放模式/历史。

#### 10.5.1 错误分类及恢复动作（已确认行为与建议的技术细化）

| 错误类别 | 典型情况 | 先尝试的动作 | 是否适合自动换下一首 |
| --- | --- | --- | --- |
| 临时网络错误 | 短暂断连、超时、服务器 5xx | 同一 `SourceProfile` 有限退避重试，尝试继续原进度；缓存可用时先用可用音频字节 | 连续播放且单曲最终失败可自动跳到下一条；主动点播则停留 |
| 播放地址过期 | 媒体签名失效，源站重新解析后可恢复 | 不更换服务器身份，重新取有效 URL/头，再从安全进度恢复 | 仍失败则视 D1 |
| 单曲不可用 | 被删、文件缺失、格式不受支持、单曲资源损坏 | 记录具体失败，若有有效完整离线版本可使用；不得自动换成其他来源同名歌 | 自动播放场景可考虑跳过 |
| 账号或服务器级阻断 | 登录失效、401/403 无法刷新、证书身份错误、明显整个源站不可达 | 终止对该源无意义的重试，展示重新登录/网络/证书提示 | 建议停止而非连跳同源多曲 |
| 本机错误 | 无文件权限、已缓存文件被删除、缓存校验失败 | 重新核验本机可访问资源，不误把缓存故障标为“服务器删除” | 按单曲/范围判定 |
| 用户主动取消 | 用户暂停、手动切歌、退出 | 中止当前恢复任务及过期重试 | **不算播放失败** |

错误状态至少要区分可恢复/不可恢复与来源范围；播放器层的错误事件和网络层 HTTP 错误应归一为 `PlaybackFailure`。`media_kit` 提供 `Player.stream.error`、`buffering`、`completed` 等事件，但 `error` 是字符串流，不能保证仅靠字符串即可可靠推导 HTTP 状态或完整错误类型，需结合音源解析/网络请求的信息。详见文末官方接口参考。

#### 10.5.2 S-007D1：不可恢复单曲的自动跳过范围（已确认）

- **正常连续播放中**：当前条目在缓存与同源有限重试后仍不可恢复，记录失败并沿已确定的顺序/随机序列自动尝试下一条。
- **用户主动点选单曲时**：此曲最终失败，停留当前条目，提供“重试”和“跳过”；不能擅自播放下一首。
- **不可恢复的来源级阻断、认证和 TLS 身份错误**：直接停止相关自动播放，不继续逐首尝试。
共同安全边界：不自动删除失败队列条目、不修改原始歌单、不跨账号或跨来源使用“同名歌曲”顶替；即便自动跳过也保留该条 `queueEntryId` 和失败原因，允许稍后重试。单曲循环模式下的技术错误不能触发无限重复，正常歌曲结束的单曲循环逻辑与错误处理分离。

#### 10.5.3 S-007D2：连续自动跳过的安全上限（已确认）

- **已确认上限：3 条不同队列曲目**。达到上限后停止自动推进，并保留队列和失败原因。
计数单位是**已确认不可恢复、触发自动跳过的不同队列条目**，不是一个文件内部的 HTTP 重试次数；一个条目多次重试仍算一次。成功播放达到可观测的稳定时间或自然完成后再重置连续失败计数，具体时长在测试中定。达到阈值后不自动回绕循环队列、不继续尝试下一轮随机顺序。若无网络、整个源站认证失败、TLS 校验失败等“继续扫队列也无法解决”的全局/来源级错误，建议不等到上限直接停止并提示。

#### 10.5.4 与 S-007B 播放模式和用户操作的关系（已确认原则）

- **仅自动连续播放路径**允许不可恢复的单曲自动跳过；用户主动选曲出现错误时停止并保持选曲目标，明确让用户手动“跳过”或“重试”。
- 顺序播放/随机播放：跳过按各自已固定的未来队列顺序进行，不能重新随机抽取或篡改原歌单；跳过记录包含失败原因和 `queueEntryId`。
- 单曲循环：正常结束循环；真正播放错误按 S-004B 恢复，恢复失败不无限重试当前曲；是否转下一条服从已确认的 D1-B 与 3 条失败上限。
- 列表循环：连续失败不因回绕而清零；不能在没有成功播放的情况下反复循环队列。
- 用户点击下一首、上一首，属于明确切歌指令，不与自动错误跳过次数混淆；取消已不适用的旧重试任务以防旧回调在新歌曲上执行 Seek。
- 如果当前队列已经没有有效下一条，停止自动推进，保留失败与队列；不擅自从其他音乐源寻找替代曲目。

#### 10.5.5 实现与验收建议（依据已确认 D1/D2）

1. 网络短暂波动时先使用缓存与有限重试，恢复成功后原进度连续播放，不误判为坏文件。
2. Emby 某个文件明确不存在且位于连续播放中：按 D1-B 在连续播放时记录失败并尝试后续条目，失败条目留在队列，当前队列来自云歌单也不回写服务器。
3. 用户手动点选的一首歌失败：停留选中曲目并显示“重试/跳过”，不会自己跳走。
4. 在关闭网络或整个服务器失去认证时，不应每秒连续跳几十首，不能清空队列。
5. 多首接连无法播放时达到连续 3 条上限就停止；随机 + 列表循环下也不能无限扫描队列。
6. 用户手动快速切歌造成的过期异步网络重试不能在新一曲上执行 Seek；仅当前 `queueEntryId` 对应的任务允许回写播放状态。
7. 用户重新打开应用后，恢复失败日志摘要可供诊断，之前确认 S-007C1 的“进程重启默认暂停”仍成立。

### 10.7 S-007 预期验收用例（S-007A/B/C/D 已确认）

1. 从 Emby 云歌单开始播放，向当前队列插入 Navidrome 歌曲，不向 Emby 发出任何歌单写入请求。
2. 云歌单被其他设备修改时，已开始的当前队列不被异步重排，除非用户明确要求。
3. 相同 `TrackRef` 在队列中出现两次时，两次播放进度、当前项与移除操作定位准确。
4. Android 播放中切回桌面/锁屏仍能从系统控制；关闭 UI 再打开正确连接已有播放会话。
5. 应用正常退出再启动可以看到原队列和播放位置；并保持暂停（已确认 S-007C1-A）。
6. 随机模式开启后跨重启不突然重复已经播放过的队列条目，关闭随机后恢复用户列表顺序；手动上一首无论已播放时长都导航到上一条，不按进度重播当前。
7. 来源被软删除或当前网络中断时，先尝试合法缓存/恢复；自动连续播放时单曲最终失败可跳过，用户明确点播时停止；连续 3 条不同条目失败或来源级阻断时停止，不跨账号替代。

## 11. S-008 音频内核、音质与播放参数设计（A/B/C/D/E 全部已确认）

> **正式已确认**：S-008A-A 三端统一 `media_kit` / libmpv、应用层 `PlaybackCoordinator` 为播放状态唯一事实来源；S-008B-Q1 第一版只使用原始音频，不引入服务器转码；S-008C 的 G1 + P2 + R1 + V1、S-008D 的 F1 + H1 + O1 均已确认。S-008E 的 EQ0 + SP1 + FX0 + HR1 + OP1 均已确认。

### 11.1 S-008A 已确认（方案 A）：三端统一 media_kit / libmpv

- Android、Windows、Linux 使用同一套 `media_kit`（libmpv）播放引擎；不在首版混入 Android Media3 播放后端或基于 `just_audio` 的另一层统一 API。
- `PlaybackCoordinator` 是应用的播放队列、随机/循环、播放进度快照、故障恢复的唯一事实来源；`PlaybackEngine` 负责执行 open / play / pause / seek 等命令和发出观测事件。
- Android 的后台媒体控制仍需 `audio_service` / `audio_session` 实测集成；Windows 的系统媒体控件（SMTC）、Linux 的 MPRIS 为平台桥接，不属于 libmpv 自带的跨平台统一能力。
- 对动态队列、混合音乐源，应用队列与 libmpv 当前内部 playlist 需要显式同步；不能每次跳到下一首都无条件销毁并重建整个引擎，否则可能破坏无缝播放。
- API 之外的特定 mpv 参数可在版本验证后通过 NativePlayer 的 `setProperty` 等能力封装，但不直接把低层 MPV API 泄漏给 UI。
- 依赖版本、原生库 ABI、后台生命周期、音频焦点、桌面发行包和资源释放需要单独实测；选择 mpv 不等于承诺 bit-perfect 音频输出。

### 11.2 S-008B 已确认（Q1：原始音频、首版不考虑转码）

- 本地文件直接读取原始音频；Emby 和 Navidrome/OpenSubsonic **明确请求原始音频字节**，不主动设定码率压缩、不依据 Wi-Fi/蜂窝网络选择音质，也不在首版实现服务端转码配置。
- OpenSubsonic 的 `stream`（可用时）请求 `format=raw` 以禁用服务端转码；Emby 使用验证过的非转码直流方式（官方 Audio Streaming 文档有 `static=true`），并结合实际服务器版本与鉴权要求测试。
- **不支持的格式/服务端不提供原始流/服务端强制转码**：按 S-007D 的单曲错误与自动跳过规则处理，明确提示“原始音频无法播放”；**不自动回退为 MP3/AAC 转码，不添加隐藏的转码参数**。
- “无转码”是传输策略，不表示 mpv 不解码（播放仍会把压缩音频解码为 PCM）；也不表示实际输出必然 bit-perfect。
- `StreamResolver` 首版只需描述 `originalAudio` 与是否支持 Range、URL 有效期、请求头等；缓存键继续包含来源/歌曲/内容修订信息，保留未来扩展 streamVariant 的可能，但不实现转码分支。
- 如果未来计划转码功能，必须另起产品决策，明确转码格式、码率、缓存、Seek、失败回退和 UI；不能把原 Q1 的“必要时转码”当作已确认行为。

### 11.3 S-008C 已确认：G1 + P2 + R1 + V1

#### S-008C1（已确认 G1）：保守无缝播放

- 使用 `gapless-audio=weak`；同参数连续曲目尽量不重建音频设备，音频输出参数有变化时允许重新初始化输出、出现短暂无声间隔。
- **不**用 `gapless-audio=yes` 强制跨采样率曲目持续同格式输出；不承诺所有混合来源和音频格式绝对无缝；不删除原音频自带静音。
- 动态队列管理须尽量避免频繁销毁/重建 libmpv 播放器；评估混合来源、随机排序、手动插队和跨曲参数变化。

#### S-008C2（已确认 P2）：有界预缓存下一首音频字节

- `PlaybackCoordinator` 根据**已确认的队列顺序**、随机序列与“下一首播放”插队规则选取预取目标；`CacheManager` 负责有界网络字节预取与临时缓冲；不通过第二个播放实例模拟预加载。其预取字节**不得作为持久分段缓存入库**（S-009A1，v2.4 已确认）。
- 在播放期间提前获取下一首的**有限音频字节**，建议从 1–4 MiB 的临时预取预算开始压测（仅为研发参数，不视为固定产品限制）；允许按照网络、音频格式、剩余播放时间与电量调整/暂停预取。未取全时只能放在会话临时内存/临时文件区域；进程崩溃或任务失效时清理，不能冒充完整缓存。
- 对不支持 Range 的音源不能误将整首文件下载成“有界预取”；对直播式、长度未知或不能安全缓存的流跳过预取。若下一首已完整缓存则直接命中本地文件；避免重复传输。
- 单曲循环不预取另一首；当前队列调整、来源停用、重复快进/跳过、应用后台策略变化、Token 失效或播放源变化时，过期预取任务必须取消或重新解析。
- 预取内容与正常播放使用一致的稳定资源身份与访问隔离；P2 有界预取**不需要也不允许**作为不完整文件持久化。只有在该曲目随后被完整接收、通过校验，且由缓存任务正式提交时，才可以成为整曲缓存；预取不自动变成已完成的持久缓存。
- 首版仅原始音频，不对预取流引入转码分支；Range 仍可用于播放 Seek 和当次有界 P2 预取，但**不能用于跨会话残片续接成缓存**；416 / ETag / 内容修订及临时 URL 的具体请求策略在 S-009B 评审。
- 需验证 Android 网络耗电、Windows/Linux 磁盘清理与首字节时延的收益；不保证所有来源都能提前取得字节数据。

#### S-008C3（已确认 R1）：ReplayGain 默认关闭，可选 Track / Album

- 设置提供 `Off / Track / Album`，默认 Off；不做自动响度分析，不修改音频文件。
- 仅按文件可用的 ReplayGain 标签调整；无标签时保持不施加 ReplayGain。处理标签不全、峰值信息缺失与切歌时增益变化；不可宣称“音量绝对一致”。
- 不默认增加预放大；避免与音量控制重复乘增益引起削波。提供音效变更后的实时回退机制。

#### S-008C4（已确认 V1）：0–100% 软件音量，不放大

- `0–100%`、静音，默认 100%；不提供超过 100% 的软件音量或额外放大；不修改系统主音量，设备分别保存其音量设定。
- Android 系统音量键调节系统媒体音量，软件音量不与音频焦点造成的暂时降低相互覆盖；Windows/Linux 系统主音量与应用音量分开管理。
- ReplayGain 可叠加在软件音量之上，但必须处理裁剪及瞬态，最终峰值和输出链需要测试。

### 11.4 S-008D 已确认：Android 系统音频与 Windows/Linux 默认输出（F1 + H1 + O1）

#### S-008D1（已确认 F1）：Android 智能焦点与中断

- 音频会话以媒体播放为用途；短暂导航提示、系统通知等请求 `MAY_DUCK` 时允许系统或应用适度降低音乐音量；避免系统自动 duck 与应用同时叠加缩放。
- 来电、暂时性失焦（`AUDIOFOCUS_LOSS_TRANSIENT`）时暂停并保留队列和进度。暂时焦点恢复后，**只有**中断前确实播放中、期间未主动暂停/停止/切歌、仍具备音频焦点和有效播放会话时，才自动继续。
- 永久失焦（`AUDIOFOCUS_LOSS`）时暂停，不自动恢复也不主动抢回；后续明确的用户播放命令可重新申请焦点。
- `audio_session` 事件接入统一 `PlaybackCoordinator`，`audio_service` 负责 Android 媒体会话/后台服务；不得发生插件与 libmpv 双重暂停/恢复。后台音频焦点的申请须满足 Android 前台服务/系统条件。
- 与 S-007C1 一致：**进程真正重启仍恢复为暂停状态**，不得把旧中断标记作为自动发声理由。

#### S-008D2（已确认 H1）：防止耳机意外断开后外放

- 有线耳机拔出或蓝牙 A2DP 断开且存在切至设备扬声器风险时**立即暂停**；该暂停原因单独记录，重新连接后**不自动续播**。
- 用户明确点击播放或耳机媒体播放键时可继续，但需重新确认输出路由和音频焦点。
- 使用 Android `ACTION_AUDIO_BECOMING_NOISY` / `audio_session.becomingNoisyEventStream` 等信号；不能仅凭“某蓝牙设备状态变化”推断一定发生危险外放，亦不能把系统通知 duck 当成耳机拔出。
- 断开与来电、手动暂停、应用退到后台同时发生时只执行一次安全暂停，禁止延迟回调在用户稍后手动播放后再误暂停。

#### S-008D3（已确认 O1）：Windows / Linux 仅使用系统默认输出

- 播放器默认始终选择系统默认音频输出设备（例如 mpv `audio-device=auto`）；**第一版不提供**应用内输出设备列表、手动绑定声卡或设备 ID 的设置。
- 用户通过 Windows/Linux 系统设置变更音频路由。系统默认设备变化时，播放引擎尽量遵从系统路由；必要时允许短时中断或重建输出，不能承诺热切换必定无缝。
- 不将“系统默认”与“独占模式”混淆；专有/独占输出尚未确认，第一版不默认启用。
- 如果系统无可用音频设备，显示清晰状态并保留队列、进度；不要静默改为空输出却向 UI 报告正常出声。
- Windows SMTC / Linux MPRIS 是媒体控制接口，不是音频输出路由器；仍需分别验证其键控与设备变更场景。

#### S-008D 已确认规则的验收

1. Android：普通导航提示允许 duck，来电暂停、焦点符合条件恢复后续播；手动暂停后不会自动续播，永久失焦不抢回。
2. Android：耳机拔出/蓝牙断开时不突然从手机扬声器出声；重连后保持暂停；用户播放命令能正常恢复。
3. Android：焦点中断、通知栏、后台服务与播放队列恢复不存在重复实例、重复状态事件或无故自动发声。
4. Windows：播放器只使用系统默认输出；系统默认设备由 USB DAC 改为内建扬声器后，输出遵循系统或清晰提示设备故障，不显示不可用的设备选择界面。
5. Linux：PipeWire / PulseAudio 常见桌面环境按系统默认设备播放，不依赖特定设备 ID；切换输出后进行实际听音验证。

### 11.5 S-008E 已确认：EQ0 + SP1 + FX0 + HR1 + OP1

> 本小节为**正式已确认产品决策**。不改变 S-008B 第一版原始音频直连、S-008C 的 G1 + P2 + R1 + V1 和 S-008D 的 F1 + H1 + O1。EQ1/EQ2、SP0/SP2、FX1/FX2、HR2/HR3、OP2/OP3 为本轮未采纳选项，非第一版交付目标。

#### S-008E1（已确认 EQ0）：不内置均衡器

- 第一版不提供五段/十段 EQ、参数均衡器、EQ 预设或复杂音色增强设置。
- 仍然执行 S-008C-R1 已确认的 ReplayGain Off / Track / Album，ReplayGain 不能被误认作新加入的均衡器。
- 不屏蔽操作系统及外接播放设备自己的均衡器；不声称能够操控系统 EQ。
- 底层保留未来扩展滤镜的封装边界，但不以“未来接口”暗示第一版已有 EQ 功能。

#### S-008E2（已确认 SP1）：0.5–2.0× 变速、尽量保持音高

- 提供用户可调播放速率 **0.5–2.0×**，默认 **1.0×**；支持快速恢复 1.0×，UI 可提供常见步进与预设，具体控件后续评审。
- 使用 `media_kit` 的 `setRate`，启用并验证 mpv 音高补偿能力；“保持音高”是目标，但不保证各种格式/设备在极端倍速下完全无伪影。
- 倍速属于客户端播放处理，**不修改原始文件，也不向服务器请求转码**；与 Seek 是独立行为。
- 各设备本地独立保存用户速率设置，播放不同来源、界面重建与后台恢复时不意外回退；与 S-007C 的进程重启默认暂停兼容。
- LRC 歌词时间定位以原音频媒体时间为准，播放器 position 应与真实媒体时间一致；通过倍速、Seek、暂停与上一首联合测试。

#### S-008E3（已确认 FX0）：首版不提供额外 DSP

- 不提供 Crossfade（交叉淡入淡出）、空间音效、虚拟环绕、压限器或额外音效增强链。
- 继续使用已确认的 `gapless-audio=weak`。**Gapless 与 Crossfade 是不同功能**，不将无缝衔接误写为两曲混音。
- ReplayGain 和倍速为明确单列的已确认音频处理功能，不因 FX0 被取消。

#### S-008E4（已确认 HR1）：高解析解码与源属性展示，不承诺 bit-perfect

- 允许 libmpv 尽可能解码受支持的高采样率、高位深原始音源，例如 FLAC 24-bit/96 kHz；具体 codec / container 仍需按打包后的平台二进制实测。
- 播放界面可展示**可信的音源文件属性**（编码、采样率、位深、声道）；不可靠或来源未提供的字段不得伪造。
- 不声称实际设备输出与源音频完全一致，不承诺 bit-perfect、独占通道或绕过 Android/Windows/Linux 的系统混音。
- 不为追求 bit-perfect 而取消已确认的 ReplayGain、倍速、音量或 Android 音频焦点处理；启用任何会改动音频信号的处理都不得宣称位完美输出。

#### S-008E5（已确认 OP1）：自动协商输出参数

- 输出采样率、样本格式/位深、声道布局和音频后端遵循系统与 libmpv 的可用协商结果，不开放用户指定 44.1/48/96 kHz 或手动指定输出格式的 UI。
- 延续 S-008D3-O1：Windows/Linux 仅使用**系统默认音频设备**；本项亦不增加手动切换设备、WASAPI 独占或其他高级路由功能。
- 用户可见的「音源采样率」与底层如能可信取得的「输出采样率」必须明确区分；不可读时不显示实际输出数值。
- 因平台设备变更而重建输出时允许短暂中断；不能向用户保证所有混合采样率曲目都零间隔切换。

#### S-008E 已确认决策的验收

1. 首版无 EQ 和 Crossfade 的用户控制项；音频处理链仍能正确启用/关闭 ReplayGain，未残留未知滤镜。
2. 0.5× / 1.0× / 1.5× / 2.0×：播放时间、歌词时间轴、Seek、暂停、切歌及状态恢复均正确；主观验证音高补偿，异常时明确反馈。
3. FLAC 24-bit/96 kHz 等测试资源能按 libmpv 的实际编解码能力播放；只报告源文件属性，不显示缺乏依据的 bit-perfect 成功标识。
4. 测试 44.1/48/96 kHz、单/双声道及系统默认输出设备变化；无手动输出采样率、独占模式和设备选择 UI。

### 11.6 S-008 验收建议（依据 A/B/C/D/E 均已确认）

## 12. S-009 整曲音频缓存、下一首预取与歌单批量缓存（产品规则评审收束，进入三端 PoC；E 的具体实现策略待实测）

> **用户最新已确认规则，优先于 v2.3–v2.5 的旧候选方案**：**产品中不存在独立的「下载」功能或「离线下载」文件类型，只有音频缓存。用户可以主动「缓存歌单」。** 整曲完整校验后才持久化；任何未完成的临时音频在任务失败、意外中断或取消后丢弃，下次重新从头获取。音乐库索引不会自动缓存全库；缓存中已有的完整歌曲可在离线时播放。S-008C2-P2 下一首有界预取为临时字节，不构成永久分段缓存；S-009B1 的主动切歌取消规则仅约束**当前正在播放歌曲的自动缓存任务**。**S-009D1 已确认所有 READY 均统一参与 LRU 自动淘汰，包括用户主动缓存歌单的曲目。S-009C1/C2/C3 的快照、任务恢复与后台调度已正式确认；S-009D2 已正式确认 L1 + M2 及 LRU 最近使用口径；S-009D3A-R2、D3B-K1、D3C-J1 均已确认**：有界磁盘安全保底、应用专属持久缓存目录、清理优先并精确撤销对应任务。

### 12.1 S-009A2 已确认：音频只有一套完整歌曲缓存

产品层只有以下两种技术生命周期，而不是「播放缓存／离线下载」双轨：

1. **播放器临时缓冲 / P2 预取（非持久音频资产）**：libmpv 实时缓冲及 `CacheManager` 为下一曲预先读取的有界音频字节，临时存在。即使含有一段可解码数据，也不得以「整首已缓存」显示或跨会话保留。
2. **应用管理的完整歌曲缓存（唯一持久音频资产）**：由自动播放缓存，或用户主动的「缓存歌单」批量任务取得；只有**原始音频整首获取完毕且完整性检查通过**，才能原子提交为 `READY`。同一来源账号、同一歌曲资源版本只需要一份受管理完整缓存；不同发起方式不复制文件、不开设独立下载目录或独立下载状态。

- **取消旧方案**：原 S-009A2「下载与缓存物理文件如何复用」A/B/C 三选一已被用户的新决定替代，**不再待评审**；没有 `OfflineDownload`、`OFFLINE_READY`、独立下载文件、独立离线下载管理页或把缓存“转成下载”的步骤。
- **用户文件保护**：设备中用户自己的本地音乐文件直接读取，不为了缓存而复制；清缓存和移除来源绝不删原始文件。封面及歌词可以沿用各自的按需缓存策略。
- **本地离线可播放**仅说明一个完整 `READY` 缓存仍位于本机且有合法播放资格，**不代表该文件被永久保护**。S-009D1-A 已确认：无论自动听歌产生还是手动「缓存歌单」得到，均可在后续 LRU 淘汰中被清理；不因曲目属于某歌单而自动重新缓存。

### 12.2 S-009A1 已确认：整首歌曲的原子缓存与失败重取

- 播放远程曲目时尝试从头获取完整**原始**音频作为缓存，**播放器不需等整首拉完即可开始播放**。音频数据接入媒体内核的桥接方式须跨平台验证。
- **唯一允许跨应用启动持久复用的是 `READY` 完整文件**；正在写入的 `*.part`、网络中断的半成品、P2 预取和 Range 局部数据都不能成为持久的可复用缓存；禁止跨会话保存零散片段或下次继续拼接。
- 本地临时任务使用 `TEMP → VERIFYING → READY` 原子提交过程；需验证预期资源大小/版本/可靠结束条件与可能的摘要，防止截断、响应替换和新旧版本混用。文件提交与数据库记录发生竞态/崩溃时应可对账。
- 缓存任务失败、被取消或进程异常退出后，清理未完成临时音频；下次请求同一歌从头获取。**即使来源支持 HTTP Range 也不进行跨会话续传缓存**，Range 只供播放 Seek/临时预取等符合设计的请求使用。
- 同一版本歌曲已经 `READY` 时，后续自动播放命中该文件；「缓存歌单」任务命中此文件则计为已缓存，不重复传输。未完成临时任务不能计为缓存命中。

### 12.3 S-009B1 已确认：切歌取消旧曲的未完成自动缓存

- 用户主动点击下一首/上一首、点选其他歌曲、通过蓝牙/系统媒体按钮切歌时，如果被切走歌曲的**自动播放整曲缓存任务**尚未完成，则取消它并丢弃临时文件，下次再听这首歌从头缓存；完成并校验成功的 `READY` 不删除。
- **用户主动缓存歌单是单独的缓存任务意图，而不是另一种文件类型**。歌单批量缓存任务不依赖用户当前正在播放哪首歌；用户切歌不能误取消歌单里尚未完成的批量缓存任务。若同一歌曲恰好同时被自动缓存和歌单缓存请求，调度器应对完整音频获取去重与正确交接任务所有权，避免切歌取消时误杀仍被歌单任务需要的获取任务。文件成功后仍只提交一份 `READY`。
- 单纯暂停播放、界面重建、锁屏或后台媒体会话仍在运行不等于主动切歌；缓存任务在这些状态下具体的执行与暂停条件属于 S-009C/E 待评审，不能以切歌规则代替。
- 提交 `READY` 与取消并发发生时，必须保障原子性：真正已验收的完整文件可提交，不完整内容必清扫。

### 12.4 S-009C 已确认：T1 + Q1 + B2（批量缓存任务）

**既定能力**：本地歌单和云歌单都有「缓存歌单」入口；用户发起批量任务，只为当次目标中尚无有效 `READY` 的远程原始歌曲获取**完整文件**。源内重复歌曲和多个任务对同一原始资源的获取应去重；本地用户原始文件不复制。此任务独立于正在播放的歌曲，切歌不能误取消仍被批量任务需要的网络获取。全部 `READY` 继续遵守 S-009D1-A 的统一 LRU，**任务完成不产生永久缓存保护**。

#### S-009C1 已确认 T1：一次性歌单快照

- 用户点击「缓存歌单」时，基于当时**已加载、可访问**的歌单条目生成**一次性任务快照**，保存歌单身份、创建时间、曲目 `TrackRef`、当时的资源修订信息（如可获取）及执行状态。对实际网络获取可按相同来源、相同曲目、相同资源版本去重，但歌单条目顺序/重复条目仍可用于原始任务展示。
- 之后原歌单新增/移除/重排曲目、重命名、云端双向同步或用户修改收藏，**均不增删本次任务的目标曲目**。再次点击「缓存歌单」才生成基于当前歌单的新快照，并跳过当前仍有 READY 的歌曲。此快照与 S-007A 播放队列快照彼此独立。
- 快照不是对来源权限的永久豁免：来源账户失效、歌单项失去访问权限时不继续越权读取。用户明确删除 `SourceProfile` 时，必须取消/清理关联任务与本机缓存（S-005C2）；其他来源的任务项不应被误删除。
- 不启用持续追踪或周期自动补齐（原备选 T2/T3 不采纳），与 S-005B 不进行后台周期音乐库扫描保持一致；歌单缓存被 LRU 淘汰后不自动重建。

#### S-009C2 已确认 Q1：持久化任务清单并在符合条件时恢复

- SQLite 持久化批量任务 ID、一次性快照、逐曲状态（等待/运行/已命中/已完成/失败/暂停/取消）、计数、可诊断失败原因和有限重试/退避信息；不存储凭证、临时播放 URL，也**不持久化任何不完整音频片段**。
- 重新打开应用、进程重建或系统允许重新调度时，读取任务元数据，重新检查用户取消状态、SourceProfile 授权、现有 `READY` 文件与网络/存储约束；**未完成的单曲从字节 0 重新获取并重新校验**，不能跨会话续传 `*.part`。
- 单首获取遇到可恢复错误时有限重试；单曲最终失败记为失败并允许其他曲目继续，保留逐项错误与重试入口；致命来源级阻断或认证失效时暂停**关联来源**的任务项，不对同一来源大量无效请求。重启后避免无边界循环重试。
- 多个任务需要同一首歌时复用同一活动获取，任务的暂停/取消只释放自身持有的需求；当无其他任务/播放需要才取消未完成的传输。在线播放优先级应优于批量获取，具体并发预算后续在 S-009B/E 技术评审中决定。
- 「已完成任务项数」反映历史结果，**当前歌单仍有完整 READY 的曲目数**应实时查询缓存状态；LRU 可能使两者不同。不允许自动永久补齐已被自动清理的文件。

#### S-009C3 已确认 B2：受平台限制的后台用户发起缓存

- Android：用户明确发起的歌单缓存，在系统许可的条件下可退至后台执行，并展示可识别的任务进度通知和停止/取消入口；Android 14+ 可评估用户主动数据传输作业（UIDT）及其他合适机制，低版本按平台规则降级。操作系统可能延后、停止或限制任务；**不保证用户强制停止应用后仍继续**，也不得通过伪造正在播放的音乐前台服务来维持网络传输。正式选用的调度 API 要按适配平台的生命周期实际验证。
- Windows / Linux：播放器**进程仍在运行**（如窗口最小化、托盘常驻）时可继续缓存；用户明确退出进程则不继续网络传输。下次启动按 Q1 恢复待办任务。
- 系统终止、权限变化或网络不可用时，可持久保留任务清单并在允许条件恢复；临时音频清理，歌曲从头缓存。**保留待办任务**不等于在任意时刻都具备启动后台工作的系统权限。
- **无后台定期库索引同步**：S-005B 的智能前台同步不受此决策改变；B2 仅适用于用户主动发起的缓存工作。

#### S-009C 验收要点（已确认）

1. 创建 100 首歌的缓存任务后，将原云歌单增至 120 首或缩至 95 首，原任务目标仍为发起时的 100 首，新增项目不自行入队。
2. 40 首 READY、某首取得 60% 临时内容时进程被系统终止；重启后保留任务元数据，40 首有效 READY 不重复获取，该未完单曲的 60% 临时文件被清除并从头获取。
3. 切歌仅取消旧曲无其他意图持有的**播放自动缓存**，不误杀独立歌单任务；同曲并发多个需求不产出重复 READY。
4. Android 后台执行受操作系统策略限制，停止后仍可恢复任务意图，但绝不宣称强停后持续下载；桌面端退出进程后不传输。
5. 来源删除立即废弃关联任务与本机缓存，其他来源仍正常；认证失效只阻断关联账号，不越权复用其他账号的缓存或凭证。
6. 对容量不足或后来被 LRU 淘汰的 READY，任务不进入「清理—自动重新下载—再次清理」的无限循环。

### 12.5 S-009B 已确认：B2-BR1 验证路线 + B3-P2-1/Seek-S1 + B4-PR1

> **S-009B2-BR1 为三端待验证 PoC 技术主路线，不代表已经成功实现；S-009B3 已确认 P2-1 和 Seek-S1；S-009B4 已确认 PR1。** 不把 mpv 内置缓冲当作应用 `READY` 缓存；第一版仍只传输原始音频、不启用转码；未完整取得的音频不能跨会话持久化。

#### 12.5.1 已确认规则在流式播放中的约束

- 无完整缓存时，用户可立即播放远程原始媒体；应用应尝试**从字节 0 顺序取得整首文件**，在同一会话内将已取得内容供播放器消费，同时向同卷临时文件写入。不能要求 100% 缓存后才开始出声。
- 顺序写入临时文件不意味着每一次 `Seek` 都可以把随机读取到的字节任意拼进完整缓存。**Seek 取得的零散 Range 字节只作当前会话的播放读取**，除非可证明同一资源、区间覆盖正确且形成无空洞的完整文件；第一版优先实施顺序完整获取，避免复杂合并。
- 接近整曲结尾但播放器先跳出时，仍遵守 S-009B1：无其他需求持有的自动缓存任务取消、临时字节删除。完整文件经可靠结束条件、长度/响应一致性及可用的版本/校验信息核对后方可 `TEMP → VERIFYING → READY`，同卷原子提交、数据库对账。
- **播放已经完整 `READY` 的歌曲**直接读取本地文件，更新真实读取/LRU；**未 `READY` 的 `*.part` 不得出现在离线可播放列表**。在线播放的当前会话可以安全读取仍在增长的临时内容，但跨进程崩溃或任务取消后不可复用。
- 源版本、签名 URL、来源权限和 TLS/HTTP 凭证始终归对应 `SourceProfile` 管理；播放桥接不得泄露实际服务器令牌到日志、其他账号或非本机网络。

#### 12.5.2 S-009B2 已确认：BR1 回环 HTTP 媒体代理为三端 PoC 主路线

**用户 2026-10-27 正式确认 BR1 的验证优先级，不代表实现能力已经通过实测。**

- **主路线 BR1**：让 libmpv 访问客户端内部受控的 HTTP 回环媒体服务（优先仅监听 `127.0.0.1`；IPv6 如启用也只可为 loopback），由代理统一协调上游原始音频请求、认证、已完成 `READY` 文件、当前会话连续递增的 TEMP 字节、Range/Seek 回应与取消操作。优先测试能否做到**同一份上游数据同时用于在线播放与整曲顺序缓存**，但不将节流/复制节省量视为已达成目标。
- **本机服务不等于可信访问**：其他本机进程也可能连接回环端口；媒体请求必须绑定随机不可猜测、短寿命、仅授予单曲/会话权限的访问票据，并做资源/方法/Host 边界校验、限速及请求结束销毁；不对 LAN 监听，不开放通配接口，不使用可被第三方猜到的自增播放 ID 作为唯一授权。不得把服务器凭证暴露到播放器媒体 URL、HTTP 响应、日志或跨来源请求中。票据出现在 URL 中须禁用代理访问日志或彻底脱敏。
- **HTTP 正确性**：对 mpv 的 GET/Range 请求区分 `200 OK`、`206 Partial Content`、`416 Range Not Satisfiable` 等状态，正确提供资源总长（已知时）、内容类型、字节区间与稳定的本次会话媒体身份；对客户端关闭连接、媒体 Seek 和服务端 URL 过期，取消无用的上游请求，不能让旧会话继续写入新资源 TEMP。
- **线程与生命周期**：验证 Android 媒体前台服务背景运行、Flutter UI 分离及重连时代理是否存活；Windows/Linux 的进程退出与代理销毁；端口冲突、端口重绑、睡眠唤醒、重试、系统网络切换、音频焦点打断和媒体切换。三端 PoC 必须实测首音延迟、长期播放、进度跳转、FLAC/MP3、取消、CPU/内存、网络与 I/O 成本。
- **BR2/BR3 保留为技术备选，而非此次用户确认的实施路线**：BR2 为原生 libmpv 自定义流回调，BR3 为远端直连播放另行顺序完整缓存（可能重复网络流量）。若 BR1 PoC 未过验收，需记录失败原因、权衡并重新评审，不自动宣布切换主路线；如临时测试 BR3 不得改变用户确认的完整缓存语义。

#### 12.5.3 S-009B3 已确认：P2-1（每曲 2 MiB、全局 4 MiB）+ Seek-S1

**P2-1 已确认的两个独立硬预算**：

- 对当前队列推导出的「下一首」P2 预取，**一次逻辑预取任务实际接收的 HTTP 响应正文网络字节累计不超过 2 MiB**（含失败重试和任何重复接收；不能通过重新尝试刷新配额）；控制已接收网络正文而非只约束最终保存字节数。
- **全局所有 P2 临时音频数据驻留合计不超过 4 MiB**（内存及临时落盘累计），仅预取当前确定的下一队列条目；任务取消后立即释放其临时数据。HTTP 报头、TLS/传输开销可独立计量和监测，但不得借此无限接收响应正文。
- 预取数据只在有效播放会话内临时使用，不作为跨会话可复用的部分缓存；只有完整整曲文件且经完整验证后才可能提交 `READY`，P2 本身不因达到 2 MiB 而产生 READY。`200 OK` 忽略 Range 时只读取预算内允许的正文并关闭任务，不得为了预取而收完整大文件。
- 预取任务因队列插播、重排、随机顺序变化、来源失效或磁盘/带宽紧张取消；重用 P2 字节前须确认相同 `SourceProfile`、同一媒体表示/版本以及连续字节位置，不可拼入不同版本的整曲 TEMP，否则丢弃重取。

**Seek-S1 已确认的处理**：

- 当前远端歌曲的整曲自动缓存保持**从字节 0 顺序取得完整原始音频**的主线；在本会话已连续可靠取得的区间 Seek 可直接读取，超出连续区间且原服务器支持可信字节 Range 时，由媒体代理发起**独立临时 Range 请求**提供所需的跳转播放字节。
- Seek Range 不混写主线 TEMP、不与主线未获得的空洞拼接、不持久化为 READY；播放器因跳转可能产生的额外带宽必须让位于当前音频实时播放需求，必要时暂停主线顺序缓存的传输，在本会话条件恢复后继续。**暂停同会话传输不构成跨会话断点续传**；进程/请求终止后的未完成整曲仍删除、下次从头。
- HTTP 的 `206` 必须检查 `Content-Range`、字节数量、原始表示、强校验版本信息（有则核验）；服务端可忽略 `Range`、返回整曲 `200`，该结果**不可伪装成所请求的后部 Range**；`416`、ETag 改变、压缩表示字节位置不稳定或不可靠的 Range 都要安全降级。若任意指定位置不可安全 Seek，明确反馈能力受限，保留可恢复状态。
- 手动切换到其他歌曲时，S-009B1 仍然生效：旧曲自动缓存若不再被用户主动的歌单缓存任务等持有，则取消并丢弃主线未完成 TEMP；完整 READY 则保留。

**历史选项处理**：P2-2（4/8 MiB）、P2-3（1/2 MiB）及 Seek-S2 为历史未采纳候选，后续不能再次称作待确认。P2-1 是用户已选定的产品级初始预算，需在三端 PoC 验证预算执行和切歌实际收益；调整预算必须另行评审。

#### 12.5.4 S-009B4 已确认：PR1 实时播放优先的带宽与并发调度

1. **优先级 1：当前歌曲可听所需的实时读取、缓冲和 Seek**；任何其他获取不得导致系统持续缓冲不足。
2. **优先级 2：当前歌曲从头顺序整曲缓存**；与真实播放读流能安全共享字节时不得另发无意义的重复上游请求。它可以临时降速/暂停以保护播放。
3. **优先级 3：用户主动发起的歌单批量缓存**；任务快照、持久队列和系统许可的后台执行遵守 S-009C T1/Q1/B2，必要时动态降速、暂停。
4. **优先级 4：P2 下一首预取**；播放缓冲充裕、接近切歌且不会持续饿死用户歌单缓存任务时可获得短时有限执行机会；如有播放卡顿风险应第一时间暂停/取消预取。

- 优先级决定资源争用时的让步顺序，不是长时间完全禁用低优先级任务；遵守每项的公平调度、取消与诊断要求。
- PoC 初始建议：实时播放流之外最多 **2 个额外整曲缓存任务**，以及**最多 1 个下一曲 P2 预取连接**。这些并发数、速率配额和触发阈值只是**待实测的技术调优参数**，并非此次用户锁定的不可修改产品规格。
- 弱网络、HTTP 429、剩余空间低于 R2 等情况降低其他任务并发直至零，确保安全；J1 手动清理、用户删除来源与 SourceProfile 权限撤销，立即撤销对应获取需求并防止 Q1 旧任务回填。
- 同一 SourceProfile 同一媒体版本被多个歌单任务、自动播放缓存同时要求时进行任务持有者去重；切歌仅释放自动缓存请求，不取消仍需该曲的批量任务，也不产生两份 READY。
- **历史 PR2 候选未采纳**：本轮正式选定 PR1，不改变已确定的缓存任务恢复、LRU 和三端 BR1 验证状态。

### 12.6 S-009D1/D2/D3 均已确认

#### S-009D1 已确认方案 A：所有完整歌曲统一 LRU

- 所有 `READY` 完整歌曲（自动播放缓存或用户主动「缓存歌单」获得）**进入同一 LRU 自动淘汰池**，不存在批量歌单缓存的永久保护标记或独立下载文件；同一个 `SourceProfile` 的相同资源版本只缓存一份，跨 SourceProfile 不自动混用。
- 只按**完整歌曲文件**为单位淘汰，不删半首 `READY`；**正在被播放器实际读取、正在验证/原子提交或有活动文件 I/O 的对象不得直接删除**，需等待引用释放后再尝试。这只是暂时读写锁，不形成永久保护。
- LRU 淘汰不会修改用户本地原始音频文件、云端音频文件、收藏、歌单、播放队列或其他来源的权限数据；不会自动重新缓存被淘汰的歌单歌曲。
- 「缓存歌单」的已完成任务项数是历史任务结果；**当前歌单实际可离线播放的歌曲数**应以当时存在且有效的 `READY` 文件实时计算；被淘汰后展示随之改变。

#### S-009D2-A 已确认 L1：各设备独立的固定、可调整缓存上限

- **Android 初始上限 5 GiB**；**Windows/Linux 初始上限各 10 GiB**。这只是初始默认设置，不是实际已预留的存储空间，也不能覆盖磁盘剩余空间安全阈值。
- 每台设备独立允许用户在设置中调整上限；具体预设档位、允许的最小/最大值、是否提供自定义 GiB 输入属于 UI/实现参数，尚未被单独确认，不强行将此前的示意档位当作已定案。
- `READY` 完整歌曲占用是受控容量的核心；进行中的整曲 `TEMP`、验证所需临时余量及 P2 有界预取会占用实际磁盘/内存，**须计入运行时空间预算和空闲空间判断**，避免在 `READY` 刚好满足上限时被临时文件挤爆磁盘。按已确认的 S-009D3 R2 保底约束执行，具体统计字段和预留时机在技术实现阶段明确。
- 缓存新曲或用户调低上限时，只淘汰可安全删除的最久未使用 `READY` 文件；如果因正在播放而无法立即达到新上限，应明确记录「待清理」，释放后再尝试，不杀正在使用的文件。
- 单个音频文件大于本机已设置的缓存预算时，不能强行越过上限或反复清理同一批歌曲；应报告「单曲大于上限，无法缓存」，在资源可用时仍可正常在线播放（不写入完整缓存），不会偷偷将该文件标成 `READY`。

#### S-009D2-B 已确认 M2：缓存管理与手动清理

- 设置页展示**当前完整歌曲缓存总占用、READY 歌曲数和各 SourceProfile 占用**；支持三个可见清理入口：**清空全部音频缓存**、**按具体 SourceProfile 清理**、**清理单首或多选歌曲缓存**。
- 清理只涉及 App 管理的音频缓存和相应缓存索引；不能清理原始本地音频、服务器端音频、收藏、歌单或播放队列。需要明确范围确认、报告实际释放空间以及活动文件延迟清理结果。
- 这些入口只操作**物理 `READY` 缓存实体**；同一首缓存被多个歌单引用，删除后所有相关歌单当前缓存命中状态都会变化，不假装每个歌单存在单独的缓存副本。
- **M3 未采纳**：第一版不要求「按歌单关联歌曲一键清理」或按大小、最后使用时间等高级筛选；基础逐曲选择与缓存状态显示保持可用。

#### S-009D2-LRU 最近使用时间语义：已确认

- 仅以下事件更新对应 `READY` 文件的最近使用时间 `lastAccessAt`：① 完整歌曲通过校验成功**正式入库**；② **真实播放命中**完整缓存；③ **实际音频读取**该完整缓存。读取频繁时允许防写放大的合并/节流更新，但不改变语义。
- **不更新** `lastAccessAt` 的事件：单纯浏览歌单、打开曲目详情、索引/扫描音乐库元数据、显示缓存管理页面、后台检查是否存在缓存。
- LRU 排序以实际访问为依据；无有效访问记录时用正式缓存提交时间作合理回退。不得因索引重建批量篡改旧歌曲的最近使用时间。
- 正在实际读取的缓存受短暂活动锁保护；锁释放后，仍按其真实 LRU 次序参与淘汰。

#### S-009D2 已确认的验收补充

1. 初次安装 Android 读取默认 5 GiB，Windows/Linux 读取默认 10 GiB；设备 A 手动调整后不改变另一台设备设置。
2. 一个近期只是被浏览但多年未播放的缓存，不会因浏览而变为最新；刚成功入库或被读取的缓存按最近使用排序。
3. 清空全部、按来源清理、清理多选歌曲都只删除对应的应用管理 `READY`；共享歌单引用的缓存状态同步变化，不碰本地音乐原件。
4. 用户降低上限时按整曲 LRU 清理；正被播放器读取的曲目不强制删除，释放后有界地处理待清理；不形成清理—重取的死循环。

#### S-009D3 已确认：R2 自适应磁盘保底 + K1 应用管理目录 + J1 精确清理

> **2026-10-27 用户正式确认 R2 + K1 + J1。** 旧版 R1/R3、K2/K3、J2/J3 只作为历史备选，不再是第一版的待决策。

**S-009D3A-R2：有界自适应磁盘剩余空间保护（已确认）**

- 以当前缓存所在物理卷容量计算保底空闲空间，独立于缓存 L1 上限：Android 首轮建议 `max(1 GiB, min(4 GiB, 卷容量 × 5%))`；Windows/Linux 首轮建议 `max(2 GiB, min(10 GiB, 卷容量 × 2%))`。**这些公式是已同意先实现并验证的测试初值，实测后允许调整，不等于所有设备都固定这些参数。**
- 启动每个整曲缓存/批量任务前检查当前实际空闲、L1 缓存预算、活动 `TEMP` 与 P2 空间及在途任务预留；空间不足先安全淘汰可删的最久未使用 `READY`，仍不足则阻止新增完整缓存并将批量任务标记为空间受阻；不删除用户原音乐或活动缓存。
- 文件大小未知时按有界增长逐步预留并捕获写入中 `ENOSPC` 等错误；任何容量查询都不能代替实际 I/O 错误处理。因空间限制无法写缓存时，在技术可行、用户授权依然有效时允许不落盘直接在线播放。
- 正在使用或正在原子提交的文件由引用/锁保护，不得为满足保底而强制删除；待文件释放再协调处理。

**S-009D3B-K1：应用专属持久目录（已确认）**

- Android 使用应用专属持久存储目录（如 `filesDir/audio-cache`），不是依赖 OS 可能提前清扫的临时 `cacheDir`；Windows/Linux 使用适合平台的应用本地数据目录。三端第一版不提供自定义缓存路径、不支持外部 SD 卡目录迁移选项。
- 受管完整 `READY` 与隔离中的 `TEMP/*.part` 放在同一存储卷，完成核验后在可行的平台上进行同卷原子改名，并协调 SQLite 记录；启动时清除孤立临时文件、对账 READY 文件/索引。
- 应用卸载后数据按平台应用存储规则处理；任何缓存清理都不删除用户已有本地音乐原文件或服务器原件。

**S-009D3C-J1：手动清理优先且精确撤销任务（已确认）**

- M2 清理提交时先记录并持久化清理意图/撤销代次（防止旧 Q1 任务复活），停止**清理范围内**新建/继续自动缓存与歌单缓存需求；受影响的批量任务项标记取消/跳过或受清理撤销，**未受影响的其他来源或歌曲继续**。
- 清理对应 READY 文件时检查活动引用；播放器仍在读取则标记待删除，读取结束后执行。取消取得一半的受影响 `TEMP`，不跨会话保留。
- 单曲被多个缓存意图持有时，用户明确清除该首应撤销所有受影响的旧意图；清理完成后 Q1 不得再自动获取。**用户以后新的主动播放或重新点「缓存歌单」属于新的意图，可再次获得这首歌。**
- 来源删除须沿用 S-005C2 的更严格本机数据清理边界；清理不会修改原歌单或服务端数据。

#### S-009D3 验收基线（依照已确认 R2/K1/J1）

1. Android 只剩少量空闲空间时启动大 FLAC 的缓存：先安全 LRU 淘汰；仍不足则不生成 `READY`，对应任务进入可恢复受阻状态，在线播放在可行时仍继续。
2. Windows/Linux 关闭并重启后，完整文件与 SQLite READY 对得上号；若 OS 临时目录被清空，不影响应用受管理完整缓存；临时残片启动时自动删除。
3. 用户在缓存 200 首的任务中途选择「清空此来源缓存」，清理完成后 Q1 不会立即自动缓存回被明确清理的同一批曲目；另一来源任务继续。
4. 播放器正在读取歌曲 A 时用户清理 A：不中断正在使用的文件读写；释放后删除并刷新缓存统计，不影响原歌单/音乐源。

### 12.7 S-009E 工程验证项：多账号隔离、整曲原子提交、损坏检测与异常恢复

> **v3.3 评审状态**：用户决定先结束缓存产品设计，剩余交给真实设备验证。既有账号隔离、完整整曲原子缓存、Q1 任务恢复和 K1/J1 的不变量仍为已确认强制要求；E-CHK 与 E-REC 方案没有经过用户逐项选择，转为 **PoC 实现候选 / 测试后定稿**，并不视为用户已经确认。可优先试做 E-CHK1 + E-REC1 作为可替换的工程基线，但必须用结果评估，不影响已确认需求。

#### 12.7.1 缓存身份与权限隔离（继承 S-003/S-004D/S-006A 已确认原则）

- 缓存逻辑主键最低包括 `(sourceProfileId, remoteTrackId, mediaRepresentationRevision)`，其中 `sourceProfileId` 表示独立配置的服务器与账号；不同 SourceProfile，即使服务器 URL、远端歌曲 ID、文件名、音频字节或媒体标签相同，**也不得跨账号共用同一物理 READY** 或借他人凭证访问。
- 媒体修订信息可以来自服务端可信的资源版本/强 ETag、文件长度/修改标记等组合；**强 ETag 是 HTTP 资源表示版本校验符，并非内容密码学散列**。弱 ETag、只有秒级精度的修改日期或仅凭相同文件长度，不能证明不同获取属于相同字节版本。版本信息不足时采取保守策略，不跨会话复用部分数据，也不跨来源去重。见 RFC 9110。
- 文件在应用专属持久目录中使用不含远端路径和凭证的随机文件名；SQLite 映射 `SourceProfile` 和 `TrackRef`，禁止路径穿越和符号链接跨目录；本机 HTTP 代理仍验证播放会话短期票据，访问日志脱敏。
- 已停用 SourceProfile 的数据按 S-005C2 保留但不主动同步；主动删除来源须撤销所有关联任务与回环票据、清除该源应用管理文件和数据，绝不触及服务器文件和用户原始本地歌曲。远端歌曲软删除但来源未被删除时，已经 READY 的完整缓存仍沿用 S-005C1 保留规则和 S-009D1 的普通 LRU；不能悄悄升级成永久缓存。
- 若服务器可证明媒体表示已经变更，应将旧版本 READY 标记为不适配**新版本播放请求**，通过新的完整获取产生对应 READY；旧文件仍须按来源软删除、空间淘汰和当前活动读者安全处理，不得当作新版本音频使用。离线时不强制向服务器验证每一首已缓存曲目，因为离线可播放是既定能力。

#### 12.7.2 原子提交与崩溃对账（实现必须满足的完整缓存不变量）

1. `TEMP`：为当前整曲获取建立同卷随机临时文件和任务标识，接收**从头连续**的原始媒体表示字节；Seek 的临时 Range 与 P2 前缀不混入此文件。
2. `VERIFYING`：检查 HTTP 请求结果、完整传输结束条件、原始表示身份/版本、已知预期内容长度与实际字节数；存在可信服务端内容摘要时验证它。若服务器未提供长度或摘要，不能仅凭「网络连接关闭」断言绝对正确，应检查协议消息完整终止、可用的容器/解码特征并根据可靠性设置保守失败规则。
3. 在 K1 同一存储卷中先写完文件并尽可能执行可用平台的文件同步，再**同卷原子重命名**为最终受管理的 READY 文件名；随后以 SQLite 事务更新映射和 `READY`、记录实际大小/源修订/本地校验值及 LRU 时间。SQLite 自身事务与文件系统重命名**不是一个跨介质的共同事务**，必须通过恢复对账处理两者之间崩溃的窗口。
4. 若崩溃发生于重命名前，清扫残留 TEMP；重命名后数据库更新前，识别没有有效 READY 映射的游离文件并安全清扫（可恢复策略另行评审，但绝不直接当作 READY）。若数据库指向的文件缺失、大小不符或校验失败，立刻使其不再可用并修正状态；绝不出现 `READY` 指向不完整/损坏文件。
5. 每次提交、用户清理 J1、LRU 和来源删除都检查同一条缓存记录的持有者、取消代次/任务版本，防止用户明确清理以后迟到的传输重新提交或 Q1 旧任务复活。删除有正在播放的活动读取者时采用延期清理。

#### 12.7.3 E-CHK 待实测定稿：已入库歌曲的损坏检测强度

- **E-CHK1（推荐）**：`VERIFYING` 时对完整文件生成 SHA-256 并保存；正常播放命中时校验文件存在/大小与缓存索引一致，并在读写异常、启动对账疑点或解码出现损坏迹象时**重新全文件计算 SHA-256**。不对每次普通播放都强制全文件扫描，减少手机磁盘 I/O 与启动延迟。注意本地散列只能用于发现文件在入库后的变化，**没有可信服务端摘要时不能证明与服务器原件逐字节一致**。
- **E-CHK2**：每次播放缓存曲目前都先完整重算 SHA-256，只有校验匹配后才允许播放。检测更积极，但大 FLAC 和大歌单会多次读取整个文件，影响首音延迟、I/O 与电量。
- **E-CHK3**：入库执行完整性检查并保存 SHA-256，但后续仅在显式错误时复验；应用正常打开缓存时仅核对文件存在。开销低，但静默截断可能直到解码失败才暴露。
- 三方案都必须在提交 READY 之前确认取得的是**完整、可靠结束**的单一歌曲文件；源端能提供可信摘要则必须校验。可用性、大小、SHA-256 各自检测不同错误，不能混为一谈。

#### 12.7.4 E-REC 待实测定稿：意外退出后的修复与损坏缓存处理

- **E-REC1（推荐）**：每次启动先对数据库执行轻量快速对账（READY 的索引与文件存在/文件大小；残留 TEMP、游离文件、未完成任务），必要时分批延后核查大库；未完成 TEMP 必须删除，Q1 歌单任务元数据保留并从零重启当前未完成歌曲。运行时发现损坏则撤销 READY、隔离/安全删除文件并记录原因；用户下次明确播放或重新缓存歌单时，按原 SourceProfile 从头获取完整新文件；**不自动遍历全部曲目进行网络回填**。
- **E-REC2**：每次应用启动完整扫描缓存库并对所有 READY 全量散列，全部核对完才认定缓存状态可用。最彻底但可能明显拖慢大型音乐库启动，且无法凭无服务端摘要的本地散列判断最初下载的内容是否与服务器完全一致。
- **E-REC3**：只清理可识别 TEMP，其他异常仅在每次真实打开相关歌曲时按需核查修复；启动最快，但 READY 列表的准确性可能滞后。
- 共同行为：检测为损坏的文件不得继续标记为离线可播放；离线无法重取时显示本地不可用，播放场景按已确认的 S-007D（自动连续播放可跳过、手动点选时停留并提供重试、最多连续三首失败）处理；来源级认证/TLS/服务器阻断按已确认规则停止。
- 修复不创建独立「下载」产品形态；缓存仍可依统一 LRU 淘汰；意外退出后**只保留任务状态和完整 READY，绝不复用部分歌曲字节**。

#### 12.7.5 S-009E 技术验证清单（待执行，不代表已测试）

1. 两个账号访问同一 Emby 服务器同一歌曲时，缓存路径/索引/凭证/回环播放票据隔离；一个账号删除不删除另一账号的缓存。
2. HTTP 正常完成、少读字节、服务器传一半断开、源文件中途变更、弱/强 ETag 差异、错误 `Content-Length`，只有真正完整可靠的单一版本文件才能变为 READY。
3. 故障注入：TEMP 正在写、VERIFYING、重命名前、重命名后 SQLite 提交前、SQLite 提交后、LRU 或 J1 删除期间崩溃；恢复后没有坏 READY，没有跨账号游离数据被读取，也没有用户清理后旧任务自动复活。
4. 缓存文件被手动篡改、截短或文件系统丢失；按所选 E-CHK/E-REC 策略发现后撤销 READY 并给出重新缓存入口；不把错误文件当作离线歌曲。
5. 同曲当前播放和歌单缓存同时持有任务，切歌只取消无其他需求的自动缓存；旧会话结束与清理/源删除并发时，不产生迟到 READY。
6. Android 进程被系统终止或 Windows/Linux 进程异常退出：保留 Q1 任务清单，清除当时所有未完成字节，重新开始未完成单曲；不使用跨会话 Range 续传。

### 12.8 已确认行为的验收基线（包含 S-009C1/C2/C3）

1. 全产品只使用完整歌曲 `READY` 音频缓存，不显示独立音频下载或“下载保护”状态。在线播放自动缓存、用户「缓存歌单」复用同一 READY 库，不复制本地原始音乐。
2. 当一首歌临时缓存到 40% 就被取消、崩溃或网络中断，临时音频会被安全丢弃；之后必须从头获取，不读入旧 `*.part` 或跨会话分段。
3. 用户主动切到别的歌曲时，如果旧曲未完成缓存只由在线播放意图持有，就取消并删除临时数据；如果歌单批量任务仍需要它，则不误取消后者的获取请求。
4. 歌单中同一来源版本的歌曲重复出现多次或被两个歌单任务同时要求时，不重复持久化同一完整文件；不同 SourceProfile 不越权共用缓存。
5. **S-009D1-A**：用户主动缓存完整歌单后，新增其他歌曲使容量超限，歌单中较旧 READY 也可按 LRU 整首自动清理，**不因为属于用户缓存的歌单而跳过**；只要文件仍被播放器读取则延后删除。
6. 已被 LRU 淘汰的歌曲离线不可播放且 UI 正确反映当前缓存缺失，不保留错误“歌单已全部缓存”的展示，不自动循环回填被淘汰的歌曲。
7. LRU 清理不会触碰设备上的原始本地音乐文件、服务器端媒体、部分进行中的音频写入或无关账号文件；删 SourceProfile 依 S-005C2 执行。
8. **S-009C1-T1**：歌单缓存任务采用创建时的曲目快照，源歌单之后变化不自动修改现有任务队列；再次用户主动发起才计算新清单。
9. **S-009C2-Q1**：任务在进程中断后保留任务状态与已完成 READY，未完成单曲临时字节被丢弃、重试从零开始；可恢复错误有限重试，并显示逐曲失败原因。
10. **S-009C3-B2**：Android 系统允许时在后台执行用户主动缓存并显示通知，系统暂停/强停时不保证持续执行；Windows/Linux 进程仍在时允许后台继续，退出后按 Q1 恢复。
11. **S-009D2 已确认**：Android 5 GiB、Windows/Linux 10 GiB 且每设备可调；手动清理支持全部、来源、单曲/多选；最近使用时间仅由完整入库、真实播放命中及实际文件读取更新，不能误删活动文件。
12. **S-009D3 已确认**：R2 有界自适应磁盘保底、K1 受管理应用持久目录、J1 精确清理且旧任务不得自动回填；建议阈值是实测参数。

### 12.9 当前阶段结论与工程待验证边界（v3.3）

- **阶段结论：S-009 缓存产品行为已足以进入开发验证，暂停逐项方案评审**；无需现在继续追问 E-CHK/E-REC 的细枝末节。
- **BR1 是已确认的三端 PoC 首选路线**，不是已证实的技术可行性承诺。未通过验证时需记录阻碍并重新审议可替代的桥接方式，不能绕过既有完整缓存语义。
- **P2-1、Seek-S1、PR1 是已确认行为**：2/4 MiB 上限、从头整曲与 Seek 临时 Range 分离、播放优先；额外并发数是待测试参数。
- **S-009E 未选定具体 E-CHK/E-REC 选项**：这些属于工程可替换策略，先依故障注入与三端性能测试评估；已确认的来源隔离、完整 READY、崩溃安全和不跨会话保留半成品仍必须实现。
- **S-010 已根据用户新指令调整范围**：本地扫描、元数据解析与路径变更的工程细节交开发阶段用真实数据验证；下一项直接评审**音乐库组织与浏览信息架构**，不改变 S-001 本地音乐作为支持来源的范围。

- 用户明确认为当前缓存功能设计已足够，剩下的问题应主要交由实际设备验证。因此**停止继续用选择题推进 S-009**；不是取消任何已经确认的缓存功能。

| P0 | 账号与源隔离 | 同一服务器两账号、两个服务器同名歌曲不串缓存/权限/票据；删除来源只清理本机该源数据 |
| P0 | Android 后台缓存 | 锁屏、切应用、播放服务活动/非活动、系统限流/中止，用户发起歌单缓存按合法平台调度执行；未完成整曲重来，任务状态持久化 |
| P1 | P2 与 PR1 | 核验每首预取实收正文总量 ≤ 2 MiB、全局临时数据 ≤ 4 MiB；播放卡顿风险下 P2/歌单任务让路 |
| P1 | LRU 与空间保护 | Android 默认 5 GiB、桌面 10 GiB 的可调预算；测试保底剩余空间、未知文件大小、ENOSPC、读中清理及用户清缓存后防回填 |
| P1 | 文件损坏与对账 | 篡改/截断 READY、删除物理文件、损坏索引、孤立文件；记录 E-CHK/E-REC 候选的首音延迟、启动时长和损坏发现率 |
| P1 | 歌单批量任务 | 混合多源歌单、重复曲目、任务创建后歌单变动、暂停/取消、进程恢复及进度通知，验证不误重复缓存、不中断无关任务 |

### 27.3 工程退出条件

1. **不会出现错误的 READY**：任何可识别的半成品、版本混淆、错误资源标识、提交中断都不能被当作完整音频使用。
2. **核心播放优先**：正常听歌、Seek、系统媒体控制和 Android 后台不中断，歌单缓存/P2 有界让路；记录实测指标，不凭主观宣称“完全无缝”。
3. **不侵犯来源与文件边界**：不跨账号共享权限或缓存，不删除用户本地原文件与服务器曲目，不将应用受管临时音频长期保留。
4. **性能参数可调整**：P2 容量等已确认上限维持不变；并发数、低磁盘计算初值和校验策略由测试评估，有变化需区分“调优参数”与“变更已确认规则”。
5. **未完成项有证据**：PoC 不通过或平台能力不足时记录复现步骤、日志（脱敏）、对应平台、对已确认行为的影响，并回到专项设计评审。

> 用户已要求 S-010 跳过本地文件扫描、标签读取的细节讨论；这些留作工程以真实文件验证。接续产品评审为 **S-010：音乐库组织与浏览信息架构**，无须先锁定 E-CHK/E-REC。


## 28. S-010：音乐库组织与浏览信息架构（S-010A/B 部分已确认，黑名单细节待评审）

### 28.1 已确认基础与本次范围

1. **S-002 已确认且不可重选**：同时具备“统一音乐库”和“独立来源”入口；统一库按具体 `SourceProfile` 聚合已启用来源的元数据，独立来源可查看某个账号/服务器的内容，二者复用同一数据库索引而非维护重复音乐库。
2. **S-006A 已确认**：跨来源歌曲不合并、不自动替换。S-010B 新确认：艺术家与专辑以统一视图组织，不刻意按来源拆开展示；歌曲 `TrackRef`、源内专辑/艺人身份和所有来源权限边界仍完整保留。
3. **S-006B/C 已确认**：我的收藏是特殊本地歌单；普通歌单有本地（可跨来源）和云端（仅单一 SourceProfile）两种。任何“歌单”页面设计必须同时容纳这些对象，不能把本地歌单错当作特定服务器的歌单。

5. **本地音乐不是近期设计重点**：S-001 的本地音乐支持保留；本地文件扫描、标签解析、路径及系统权限实现方案暂不列为 S-010 需要用户选项。开发阶段用实际 FLAC/MP3/M4A/多艺术家与嵌入封面等文件样本，以及 Emby/OpenSubsonic 实际字段做行为与兼容性测试；不在设计阶段假设文件标签结构完美或字段全都有。

### 28.2 音乐库组织：已确认方向与开发期验证项（S-010B）

- **歌曲（Tracks；已确认）**：按具体 `TrackRef` 保留全部条目。同一录音分别存在于 Emby A 与 Navidrome B 时，仍显示为**两首来源不同的歌曲条目**；不自动查重、合并、替换、更改原歌曲 ID；列表行可以轻量显示来源，但不得强制先按来源浏览。
- **艺术家（Artists；统一展示已确认）**：统一音乐库首先让用户按歌手浏览，不默认将同名歌手拆成多个带来源标签的顶级项目。可建立**只用于本地浏览的聚合视图/关系索引**，把多个来源的源内艺术家记录映射到一个可读的展示项，其下展示来自各来源的专辑和独立歌曲条目；源内 artistId、`SourceProfile`、权限和关联关系不得被覆盖。碰到同名异人、别名、多艺术家等情况，匹配质量与纠错入口用真实数据设计验证。
- **专辑（Albums；统一展示已确认）**：统一音乐库不以音乐源为默认拆分维度。建议按标准化专辑标题、专辑艺术家及可辨发行/版本信息建立**浏览聚合候选**；打开后显示各来源的原始歌曲条目，重复歌曲照样独立存在，可辨认具体来源。不同版本、同名不同专辑的误合并风险必须用真实数据验证，**不等于把多个服务器的专辑 ID 合并为一个远端 ID**。
- **歌单（Playlists；既有决策不变）**：我的收藏为特殊本地歌单，本地歌单可混合来源，云歌单只归属一个 SourceProfile 并双向同步；聚合艺术家/专辑的曲目列表不能改变这一编辑权限约束。
- **独立来源（Sources；已确认）**：仍提供 SourceProfile 单独浏览入口，针对某个账号查看其歌曲、专辑、艺术家和云歌单；用户主动进入单来源时，该范围限定有效。
- **排序（已确认常用功能）**：歌曲提供标题、艺术家、专辑、最近添加等常见字段；专辑提供名称、艺人、发行年份/日期等；艺术家提供名称排序。可用字段才开放相应排序，支持升降序、稳定次序；中文与拉丁文字、缺失字段等用真实数据验证。无需在首版强制实现复杂、可跨设备同步的排序配置。
- **来源筛选（辅助功能；交互未定）**：已确认可以进入单来源页，统一视图以全部已启用来源为基准；来源筛选是否使用多选及具体控件尚未明确，筛选只能影响视图，不能改写曲目、播放队列或云歌单。
- **黑名单（已确认仅具体歌曲）**：允许用户手动按精确 `TrackRef` 加入与撤销；不会自动识别“重复歌曲”并黑名单，也不针对艺人或专辑整体屏蔽。歌单/缓存/来源原数据不能仅因加入黑名单被删除。**仍待工程验证**：黑名单在统一列表、搜索、自动队列及已有歌单/队列中的可见性策略。
- **缺失或停用**：停用来源与服务器已确认缺失曲目遵守既有 S-005C；个人歌单/收藏中的历史引用依既有规则保留或标记不可用，黑名单规则不能悄悄覆盖这些来源生命周期决策。

**身份模型不变**：聚合艺术家/专辑是本地阅读层概念，并不建立跨服务器可写身份。所有播放、封面获取、缓存和远端操作最终都必须追溯至原来的 `SourceProfile` 和稳定的源内条目 ID。

### 28.3 S-010A 已确认（方案 A）：分类直达 + 独立来源入口

**用户正式确认方案 A**，具体行为：

1. 进入「统一音乐库」后直接访问并切换四个分类：**歌曲、专辑、艺术家、歌单**。分类是主信息架构，不要求先经过最近播放、最近添加等概览首页。
2. **独立音乐源入口必须保留**：用户可选择具体 `SourceProfile`（同一服务器的不同账号仍分开）进入其专属歌曲、专辑、艺术家以及所属云端歌单浏览范围。
3. 统一分类页的数据来自既有来源索引，分类与单源入口共享条目身份和已确认的来源权限边界；独立来源不是另一套重复索引。
4. 「我的收藏」保持为特殊本地歌单；本地歌单可混来源；云歌单只归属单个来源。分类直达并不改变 S-006C 歌单模型。
5. **未定且不得假装已确认**：Android 与桌面端具体导航控件形态、第一次打开默认选中哪一分类、是否记住上次分类、歌单是否另有快捷入口。首版不建设独立「概览优先」或「可切换双首页」模式；未来如有需要再另行提案。

### 28.4 S-010B 已确认方向、保留边界及黑名单待定项

#### 28.4.1 S-010B1 已确认：统一艺术家/专辑，不刻意按来源拆分

1. 用户明确希望减少多音乐源造成的割裂感。统一库中的“艺术家”和“专辑”应按**音乐内容组织浏览**；可将不同来源指向相同展示艺术家/专辑的记录汇集到一个浏览页面，不要求用户在顶级列表先决定来源。
2. **仅展示聚合，不把来源实体视为同一个可写/可播放对象**。每条歌曲、每个源内艺术家/专辑引用保留来源身份；同一首歌跨来源出现多次仍显示多条。播放和缓存不自动从 Emby A 切换到 Navidrome B，保持 S-006A。
3. **聚合键为开发实现提案，非已经确认的精确匹配算法**：艺人名称的清理/别名匹配，专辑名+专辑艺术家+版本/发行信息候选分组；同名不同人、同名不同专辑、豪华版与普通版、合辑、多艺人情况都必须基于真实数据测试。不得只凭标题猜测歌曲身份或去重。必要时允许未来增加手动拆分误分组的功能。
4. 从某一个 SourceProfile 单独浏览时只展示该源的数据；统一库默认不强制添加来源筛选条件。页面可在必要时提供来源标识、查看原始条目或筛选入口，但不以来源为导航主轴。

#### 28.4.2 S-010B2 已确认：常见排序即可

- **歌曲**：标题、艺术家、专辑、最近添加；音频时长为可用时的辅助排序。
- **专辑**：专辑名称、专辑艺术家、发行年份/日期；最近添加数据可信时可选。
- **艺术家**：名称排序为基本功能；不强求复杂热度计算或人工自定义权重。
- 排序可切换升/降序；相同排序键以稳定的聚合 ID 或 `TrackRef` 作次级键，不因数据同步导致无意义跳动。缺少元数据的歌曲仍显示，不能丢失。
- 具体默认排序方式、记忆用户选择和界面控件可以在实现/设计中选择常用做法；本轮用户没有指定必须按标题还是必须按最近添加，不得误写为已正式选择 S-010B2 原 A/B/C 中的某一套默认值。

#### 28.4.3 S-010B3 来源筛选：简化为辅助能力，具体交互尚未确认

- 统一歌曲/专辑/艺术家默认从全部已启用来源构建视图；**不强制按来源分区**。来源筛选只是用户主动缩小范围的功能，不修改底层聚合、曲目 ID、播放队列、缓存或云端数据。
- S-002 确认的“独立来源入口”继续存在，并能精确浏览一个 SourceProfile。是否在统一页提供单源或多源勾选筛选、具体入口和默认筛选持久化方式，留给后续 UI/搜索设计，不在本轮增加必选方案。

#### 28.4.4 S-010B4 已确认：仅具体歌曲黑名单

- 用户手动加入、移除黑名单；**不做歌曲自动去重**，也不会自动根据标题把同名歌曲加入黑名单。
- 建议黑名单采用本设备本地记录、支持撤销；若针对歌曲，身份必须是具体 `TrackRef`，确保只隐藏用户选择的 Emby A 歌曲而不误处理 Navidrome B 同名歌曲。
- **用户已正式选定 X1**：黑名单只能添加具体的歌曲 `TrackRef`，不包含艺人、专辑级屏蔽；同名同曲在另一个账号/服务器中不会被连带加入。具体来源的整库显示/停用仍使用既有 `SourceProfile` 功能。
- 供后续确认的效果：只在统一库/搜索隐藏，还是自动生成播放队列时也跳过；已存在收藏、歌单和当前队列是否继续保留并标记为黑名单项目。**不允许黑名单直接删除服务器音乐、本地源文件或现有远端歌单条目**。
- 有效的源实例删除时，按 S-005C2 清理其关联的本机黑名单记录，不能留无法回溯的悬挂引用。

#### 28.4.5 核心验收用例（当前可验证行为与待确认黑名单分离）

1. Emby A、Emby B、Navidrome B 各自含同名歌手/同版本专辑：在统一艺术家/专辑页优先以统一内容浏览，点击进入展示多个来源的歌曲条目；原始来源身份可追踪。
2. 同一录音位于两服务器：统一歌曲列表和聚合专辑页面均保留两条独立歌曲记录；不得偷偷去重、替代或改变缓存的 SourceProfile 关联。
3. 同名不同歌手与同名不同版专辑的数据集：不应强制隐藏一条真实数据，若聚合规则无法稳妥判断必须提供保守区分或未来人工纠正途径；具体算法由开发阶段真实样本决定。
4. 中英文标题、数字、专辑年份缺失：常用排序可用且次序稳定，不影响现有播放队列。
5. 手动黑名单至少具有可添加与撤销操作；对何种对象生效以及影响哪些视图/播放操作，**必须等待 S-010B4 选择后才补写最终验收细节**。
