# 分块缓存参考分析：棉花音乐与 SylphyMusic

2026-10-29，继续分析用户提供的棉花音乐 4.13.7 `base.apk`。样本身份、摘要及静态分析边界见 [后台持续播放学习清单](BACKGROUND_PLAYBACK_LEARNING.md)。本次只分析和整理文档；未修改业务代码、安装运行参考软件、编译或执行功能测试。以下建议均为待办。

## 结论

它使用 **按资源字节位置组织的片段缓存**：已缓存的 span 与未缓存的 hole 分开表示，读取时切换磁盘与上游，缺失区间写入有范围锁，已写片段可以独立提交、索引、复用和淘汰；完整后还有迁移成单文件的路径。

这比我们目前的“内存前缀预取 + 完整文件缓存”更适合保留未播完、拖动后或网络中断前已下载的数据。值得学习的是 **区间复用和共享写入的协调**，而非某个固定分块大小或换一种编程语言。

分块缓存可以减少重连后的重复下载、减轻短时网络波动影响，但不能让被系统暂停或结束的进程自动继续执行。此次后台问题仍应优先落实 [P0 清单](BACKGROUND_PLAYBACK_LEARNING.md)：取消隔离、代理探活、串行恢复和原生/Dart 故障证据。

## 已确认的实现

| 机制 | APK 中的代码证据 | 可以作出的判断 |
|---|---|---|
| 区间模型 | `fragment` 模块包含资源 key、position、length、时间戳、文件信息；`CacheDataSource` 有 `next span isCached` / `next span not cache` 分支 | 缓存单位是某资源的连续字节区间，不要求先下载完整首部到尾部 |
| 多数据源切换 | 存在 `cacheReadDataSource`、上游数据源、缓存写入数据源和 open-next-source / read-position / bytes-remaining 状态 | 一次读取可以在已有片段和缺失数据之间切换，而非只在“整曲已缓存/未缓存”两种状态间选择 |
| 片段上限与滚动提交 | CacheDataSink 接收 fragmentSize；实际读写包装器达到当前片段容量时先提交，再打开下一文件，并按剩余容量截取每次写入长度 | 网络读取缓冲和磁盘片段是不同概念；持续读取可以落成多个片段 |
| 范围写锁 | `startReadWrite`、`startReadWriteNonBlocking`、`lockRange`、`releaseHoleSpan`，提交/释放时 `Condition.signalAll`，等待路径有 `Condition.await` | 以缺失区间为单位协调写入，其他读取方可以等待已提交数据；不能仅凭这些代码认定所有取消路径均正确 |
| 持久化索引与启动加载 | `.v3.exo` 片段文件、`.uid`、`cached_content_index.exi`、目录扫描、元数据与文件索引更新 | 可重新发现已提交片段，具备跨启动复用的结构；断电、半提交和损坏文件的全部处理仍未设备确认 |
| 分片淘汰与访问更新 | cacheEvictor 按容量移除 span；其比较器按片段访问时间排序，touch 更新文件索引/时间信息 | 使用片段粒度的 LRU 思路，而非只能删整首歌曲 |
| 完整文件层 | `CopyToOneCacheDataSource` / `OneCacheUtil`，存在 `not cache all`、完整文件检查和片段迁移分支 | 片段缓存与完整文件是两层，不应把已有一部分片段等同于完整离线歌曲 |
| 迁移清理保护 | 片段迁移路径存在 `have other request not delete span`，并有 `isDeleteSpanCache` 分支 | 完整文件可用后不一定立即删除所有旧片段，会考虑其他请求；不能由此断言全部读者租约实现无缺陷 |
| 预加载接入 | `SongCacheManager.createMediaCache` 将 fragmentLength、cacheEvictor、fragmentCacheDir 等参数传入分块路径；存在 `FragmentPreloadTask` | 分块能力被应用缓存装配与预加载引用，不只是 APK 内一个孤立的库类 |

上述 API、文件格式和日志语义与 ExoPlayer/Media3 的 SimpleCache 模型相近，但这里包含自有包名和改造。没有据此确认其具体上游版本或全部源码来源。

### 块大小能够确认到什么程度

- fragmentSize 是传入参数，SongCacheManager 有 fragmentLength 参数；尚未完成所有配置来源和播放分支的追踪，**不能宣称该版本始终固定为某个块大小**。
- 写入器对小于 `2097152` 字节的片段发出性能警告，即推荐避免过小于 2 MiB 的文件碎片；这不是默认值的证据。
- 该写入器配置的内存缓冲为 `20480` 字节（20 KiB），它也不是磁盘分块大小。
- 分块落盘不代表“每块必定独立发一个 HTTP 请求”，也不代表已经确认存在多连接并行下载；网络 Range 和磁盘文件切分应分别分析。

## 一个区间复用例子

以下数字仅用于说明模型，不是样本中的实际配置。若已经缓存 `[0, 8 MiB)` 和 `[16, 24 MiB)`，播放器请求 `[4, 20 MiB)`：

| 需要的区间 | 数据来源 |
|---|---|
| `[4, 8 MiB)` | 读取已有片段 |
| `[8, 16 MiB)` | 只为缺口回源，并提交新的可复用片段 |
| `[16, 20 MiB)` | 接回已有片段 |

这样在拖动、重新连接或重启后，不必把已取得的片段全部重下。真正离线播放还要求后续需要的区间可用；有片段不等于整曲完整。

## 与我们当前实现的差异

| 方面 | SylphyMusic 当前实现 | 分块模型可带来的改进 |
|---|---|---|
| 完整缓存 | 完整长度与 SHA-256、本地原子提交后才 READY | 保留这个完成标准，增加独立的“已提交片段”层，不降低完整缓存要求 |
| 未完成数据 | TEMP 文件启动时清理，不作为可复用完整缓存 | 对已验证并独立提交的片段做持久化；仍清理未提交 TEMP |
| 前缀复用 | AudioPreview 在内存中保存前缀，强 ETag 一致时可与后续 Range 合并 | 扩展到磁盘上任意已缓存区间，并可跨会话复用 |
| 任意 Range | 已支持回环代理 Range、完整文件读取及前缀复用，**不是缺少 Range 支持** | 缺少的是持久化的不连续区间索引和缺口调度 |
| 下载与播放 | 按 TrackRef 保存活动传输、下载需求和取消标记；同曲任务可能等待整个活动 relay 结束 | 以消费者需求与缺失区间协调共享写入，减少等待整曲和重复开流 |
| 淘汰 | 完整歌曲 LRU、读取租约和延迟删除 | 为片段增加预算与 LRU，仍保留播放读取租约，避免删掉活跃读者所需文件 |
| 身份与一致性 | 来源独立的 TrackRef、resourceVersion；前缀拼接要求强 ETag 与精确 Content-Range | 分块必须继承这些边界，不能只按裸 URL 或标题共享片段 |

## 值得学习的实施清单

| 建议顺序 | 改进 | 与后台持续播放的关系 | 必须保留的边界 |
|---|---|---|---|
| 先于分块 | 隔离播放消费者与离线任务的取消所有权 | 防止系统暂停下载顺带断开播放；这是现有代码更直接的风险 | 用户停止、来源停用、退出仍应正确关闭对应读取 |
| 第一阶段 | 明确缓存三层：未提交临时数据、已提交片段、完整 READY 文件 | 中断后保留可靠进度，同时不误报可离线 | 每片段有范围/版本/长度信息；需要时有本地摘要，完整文件仍经过最终校验 |
| 第一阶段 | 增加持久化的区间索引和缺口查询 | 重连、Seek 和恢复时只下载缺口 | 区间无越界和冲突；跨账户与来源不复用；持久化变更提供前向迁移 |
| 第一阶段 | 先做小范围的顺序片段持久化，再考虑任意 Seek 片段 | 控制改动范围，先取得断线复用收益 | 不直接把现有残片目录当成可信片段；只有独立校验提交后才复用 |
| 第二阶段 | 缺口单写者与可取消等待 | 播放、预取、下载可复用同一区间，减少竞争与网络活动 | 等待要有取消和时限；写入者失败/退出/来源撤销时释放锁并通知，不形成永久空洞锁 |
| 第二阶段 | 消费者订阅与播放优先级 | 停止某个下载订阅不应停止仍被播放使用的共享工作 | 来源撤销属于更高层终止，不因其他订阅存在而继续联网；同源不同资源版本不共享 |
| 第二阶段 | 分片 LRU 与读取租约 | 避免只听一部分就保留整曲成本；保护正在消费的缓冲 | 当前读者文件不被提前删除；缓存与完整文件阶段性重复占用计入预算 |
| 第二阶段 | 完整覆盖后合并/提升为整曲文件 | 最终仍能走当前稳定的本地完整文件播放路径 | 必须证明同一版本的区间并集恰好覆盖 `[0, total)`，仅累加字节数不足以证明无洞/无重叠 |
| 以后再决定 | 根据测得的命中率、启动成本、文件数和写入开销调整片段上限 | 在短时波动恢复效率与磁盘开销间取舍 | 不照搬样本数值，不在没有需求时默认多线程并行、大范围预下载 |

此处是机制建议，不主张直接改用 Media3 或复制反编译代码。可以在现有 Dart / SQLite / 回环代理架构中实现区间存储，但这属于缓存结构升级，不是几个超时参数的修补。

## 不宜照搬或尚未确认的部分

1. **不能用块长度代替内容一致性。** 在已抽取的 fragment 模块中没有找到明确的强 ETag / If-Range 或 SHA-256 调用；上游其他模块可能还有处理，不能断言它完全没有。我们已有的资源版本和强验证规则应保留。
2. **本地摘要不证明远端版本相同。** 摘要可发现片段本地损坏，跨请求拼接还必须核对来源身份、资源版本、总长度和可信的验证信息；不能混合旧歌和新歌的同一偏移。
3. **缓存命中并不意味着请求已完成。** 大 Range 可以跨多个片段和空洞；需要正确返回长度、偏移、HEAD、后缀和失败状态，不能拼错或无限等待。
4. **未知长度要单独处理。** 样本存在未知长度分支，具体行为未完整追踪；我们的方案不能把“连接 EOF”直接当作可信完整提交。
5. **片段文件提交不等于断电事务保证。** 样本可见 flush、close、索引登记与启动扫描，但尚未确认 fsync、文件/数据库事务和所有崩溃恢复顺序。我们的新层需要明确提交协议和孤儿片段清理。
6. **范围锁不等于完整取消隔离。** 样本的范围锁、等待和通知是真实机制；没有完成所有下载/预取/播放订阅的生命周期追踪，不能宣称已经证实它不会互相取消。
7. **磁盘分块不等于网络保活。** 即使有很多本地片段，未缓存的后续区间仍需要进程、网络和播放器继续工作；缓存不能替代媒体前台服务和故障恢复。

## 对本次后台问题的建议

当前优先顺序应为：

1. 先处理后台清单里的取消隔离、代理探活和恢复，获得“哪一层卡住”的证据。
2. 再将可靠前缀/顺序片段持久化，增加恢复后的复用能力，记录已提交区间、缺口、最后供数阶段与等待原因，不记录私人地址或媒体身份。
3. 确认有明显收益后，再扩展任意 Range 的片段共享、淘汰和整曲提升。

用户后续观察重点是：播放中途断网再恢复是否少重下、Seek 后旧区间是否复用、暂停同曲下载是否影响声音、进程重启后能否复用已提交片段、资源版本变化时是否丢弃旧片段。此处仅列观察目标，本轮未运行这些场景。
