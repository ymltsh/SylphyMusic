# 后台持续播放：参考分析与改进清单

2026-10-29，根据用户提供的棉花音乐 APK 和当前 SylphyMusic 代码整理。本文是分析和待办，不代表实现完成，也不授权自动安装、修改系统设置或发布。此次只修改文档，不修改业务代码、不编译或执行功能测试；后续功能和设备验证由用户负责。

## 结论与证据范围

现阶段最值得学习的是 **代理自检与恢复、恢复操作串行化、播放与下载的生命周期隔离，以及有界失败处理**。没有证据表明需要先更换播放内核，或把 Dart 代理迁移到独立进程。

样本为棉花音乐 / Cotton Music `com.caij.puremusic` 4.13.7，versionCode 40130071、minSdk 24、targetSdk 35，SHA-256 为 `E41EB8C1F8B6864AE57220D79FD3CCABAB7B55EAFED75C3B7745F0FC827690EC`。只做静态分析；代码强混淆，未安装运行，未验证设备上的长期播放效果，也不能排除 split、动态代码和系统设置影响。

下面将“参考 APK 中确实存在的设计”和“根据我们自己的风险提出的建议”分开记录。借鉴机制，不复制反编译源码；不把类名、SDK 自带代码或权限声明直接当作有效保活证据。

## 参考软件已确认的设计

| 编号 | 设计与证据 | 可以学什么 | 尚不能据此确认什么 |
|---|---|---|---|
| R1 | `PureMusicPlayService` 声明并实际启动 `mediaPlayback` 前台服务，提供媒体浏览服务接口 | 播放生命周期归媒体服务管理，不依赖 Activity 可见 | 不能保证厂商系统绝不结束进程 |
| R2 | `PlayManager.checkPing` 调用 `ProxyManager.ping`，返回失败时调用 `restart`；存在对应诊断字符串 | 恢复前识别本地代理是否健康，而非所有失败都重新打开音频 | 未证明它按固定周期探测，或能发现所有上游故障 |
| R3 | `checkPing` 有互斥锁，代理 start/stop 也存在互斥保护；restart 顺序为 stop、延迟 2000 ms、start、再延迟 1000 ms | 同一时间只做一次恢复，先处理旧资源再建新资源 | 固定等待不等于证明所有旧连接都已排空，时长不宜照搬 |
| R4 | `Pinger` 真实请求本地 `ping` 路径并检查 `ping ok`，有尝试计数与失败返回；初始化注入独立 `pingHttpClient` | 不只检查端口或对象是否存在；探测流量与音频转发分开 | ping 成功仅证明本地响应路径通畅，不能证明 Emby 正常供数 |
| R5 | `PlayManager` 有按曲目标识计数的错误处理，包含 `io_error_retry`、`error retry current`、`error retry next` 和停止分支 | 同曲重连、下一曲和停止有边界，避免无限重试 | 当前未完整还原各错误类型与所有计数重置条件，不照抄次数 |
| R6 | 曲目结束处理获取 `pure:player` PARTIAL_WAKE_LOCK，最长 30 秒并有释放路径；耳机按键有最长 10 秒短锁 | 特别保护切歌和熄屏按键等过渡阶段，锁要有明确释放与上限 | 不能把短锁解释为整个下一曲准备阶段必然都受保护 |
| R7 | 代理存在 `NoCacheProcesser.requestOnly` 转发路径，播放侧有下一曲预加载组件 | 缓存与转发可以分层，预加载可减少切歌时临时准备工作 | 未证明磁盘异常会自动走无缓存路径，也未确认所有预加载条件 |
| R8 | 包含 ExoPlayer CPU/Wi-Fi 锁管理代码，也包含 `MpvMediaPlayer` | 可以研究按播放状态管理设备资源 | 未证明主播放分支启用了 Wi-Fi 锁，不把打包代码等同于实际配置 |

补充：参考播放服务 `onStartCommand` 返回 `START_NOT_STICKY`。Manifest 中未发现专门的代理 Android Service 或代理独立进程。因此当前不能将它的持续播放归功于“代理单独保活”“无限拉起”或“天然绕过后台时限”。

## 我们值得实施的清单

优先级表示建议实施顺序；均为待办。第一批应集中在 P0，不同时引入多种保活机制，以免无法判断改善来自哪里。

| 优先级 | 改进项 | 当前依据与缺口 | 建议行为及用户观察标准 |
|---|---|---|---|
| P0 | **下载暂停与播放转发隔离** | 自身风险：`CacheJobs.pause()` 按 running 曲目调用 `cache.cancel(ref)`；`captureRelay` 也使用 `_active[ref.key]`，取消回调会关闭播放上游。同曲离线任务等待播放 relay 完成时可能被波及，尚未设备复现 | 区分下载需求、播放读取和可选缓存写入的取消所有权。系统超时或暂停离线任务不关闭仍被播放使用的连接；来源停用和用户停止播放仍按既有规则终止读取。观察：暂停同曲下载后声音继续，来源停用后仍立即停止 |
| P0 | **本地代理健康检查** | 借鉴 R2/R4：当前 `MediaProxy` 启动后无健康端点和自检恢复；`port != 0` 不等于可响应 | 增加仅回环可用、无媒体数据的有界 HTTP 探活。启动、恢复播放及故障时检查；持续有进度时不频繁探测。观察：日志能区分本地代理失败与上游无数据 |
| P0 | **代理重启与恢复统一串行执行** | 借鉴 R3：现有播放代际校验能挡住部分过期重试，但不等于统一串行取消 native open 和代理处理 | 同一播放会话只允许一个恢复任务。关闭匹配的旧连接、等待可取消工作结束、重建必要组件、生成新票据、按位置恢复。用户暂停、换歌或停用来源使旧恢复失效。观察：无重复开流、无暂停后被自动播回 |
| P0 | **打开和切歌卡住后的处理** | 自身风险：45 秒无进度恢复在 `_opening` / `_finishingTrack` 时不执行；50 秒检查只记录 `open_stalled` / `transition_stalled` | 为原生操作设计可取消、可确认完成的边界，必要时重建播放器；不要只 `Future.timeout` 后并发再次 open。超出预算后给出可操作状态。观察：卡在曲末或打开音频时可恢复或明确停止，不永久等待 |
| P0 | **原生与 Dart 两侧的故障证据** | 自身需要：现有诊断主要是 Dart 阶段事件，无法可靠区分进程被杀、Dart 不推进、代理失活和网络停滞 | 原生记录服务创建/销毁/timeout、前台启动成败、CPU 锁持有情况、播放意图、音频焦点、网络类别、Doze 状态；Dart 记录事件循环心跳和转发阶段。恢复后用会话标识与退出原因辅助判断，禁止把一次心跳延迟直接认定为卡死。不记录地址、票据、来源/曲目 ID、私人元数据或系统退出描述原文 |
| P1 | **票据过期与远端鉴权错误分开** | 自身风险：本地票据固定 2 小时到期，再次 Range 请求会被拒绝；这不是系统时限，也不等于 Emby 凭据失效 | 用内部失败类别区分本地票据过期、来源撤销、远端 401/403 和 TLS 错误；合法当前会话可有界换票，不延长已撤销票据的权限。观察：长音频/长暂停后的继续播放不会因本地过期被当作账号失效；不能绕过真实鉴权失败 |
| P1 | **分阶段恢复与重试预算** | 借鉴 R5；我们已有最多两次同曲重连和连续失败停止，不能描述为完全缺失 | 在现有边界上区分本地代理恢复、上游重连、临时网络不可用和不可重试错误；限制总次数与总耗时。观察：网络短断能恢复；无网络时不无休止跳过曲目、反复建连或刷写诊断 |
| P1 | **可选缓存失败不阻断播放** | 借鉴 R7 的分层思路；我们已有空间检查失败转为纯转发、体积超限时放弃缓存的路径，仍需检查全部写盘/提交和取消边界 | 明确播放读取高于可选缓存写入；磁盘不足、缓存淘汰或下载暂停应尽量降级为继续转发，未完整提交的数据不得 READY。观察：取消缓存、配额不足不会顺带掐断当前声音 |
| P2 | **Wi-Fi 熄屏稳定性选项** | R8 只有库代码证据；我们未显式实现 WifiLock，不能确认为根因 | 仅在设备上出现 Wi-Fi 专属问题后做对照；锁随在线播放需求获取，暂停/停止/退出释放，不覆盖来源撤销。观察：与移动网络、本地音频和不持锁状态比较，并留意耗电；不把锁当作 Doze 豁免 |
| P2 | **检查切歌和熄屏按键的保护连续性** | 借鉴 R6；我们已按 `_playRequested` 持有持续 CPU 锁，正常情况下覆盖缓冲和切歌 | 先从原生日志证明是否真有锁空隙，再决定是否增加短期过渡租约；不叠加永久锁。观察：曲末、远端准备、按键恢复期间保护连续，真实暂停后资源释放 |
| P2 | **下一曲预取的完成/失败边界** | 借鉴 R7；我们已有前缀预取、版本校验、取消代际和超时 | 继续限制预取预算；预取失败不影响下一曲正常开流，切歌后可取消旧计划。已有缓冲优先级规则继续保留。观察：预取未完成、过期或网络变更时仍可正常切歌，不因优化路径卡住 |
| P2 | **用户可见的后台诊断入口** | 自身建议，不是已确认的参考软件功能；系统省电策略可能因设备而异 | 显示已知电池优化/后台设置状态，提供用户主动进入系统设置和导出诊断的入口；不保证“无限后台”，不自动更改设置。Android 11+ 可辅助读取 ApplicationExitInfo，Android 10 使用会话/服务记录，不能捏造退出原因 |

## 第一批建议范围

1. 增加原生状态和代理阶段诊断，日志开关沿用现有主动启用机制。
2. 隔离离线任务暂停与播放连接的取消路径，保留来源撤销边界。
3. 增加本地代理探活和受播放代际约束的单次恢复入口。
4. 为 native open / 曲末卡住补齐可取消操作设计；可先交付前三项的诊断版本，再依据用户反馈落地重建策略。

不建议第一批同时迁移原生代理、改播放器、修改省电策略、加大缓冲并加入 Wi-Fi 锁。多个变量一起变化会掩盖故障原因，也增加资源释放与耗电风险。

分块缓存的进一步调查见 [分块缓存参考分析](FRAGMENT_CACHE_REFERENCE.md)：可学习区间复用、缺口锁、独立片段提交和完整文件提升，但应放在上述 P0 隔离与恢复机制之后，不把缓存结构升级等同于系统保活修复。

## 故障应该如何归类

| 用户现象 / 记录 | 优先怀疑 | 下一步判断 |
|---|---|---|
| 返回应用后出现新进程会话，存在系统退出记录 | 进程结束 | 看退出类别、前台服务此前是否仍在；不归因于代理单独被暂停 |
| 原生记录继续，Dart 心跳和代理请求同时不推进 | 引擎/事件循环停滞或调度问题 | 比较活动、服务和音频状态；单次心跳延迟不足以定性 |
| 本地 ping 失败，但进程与服务仍在 | 代理监听/处理链路问题 | 有界串行重建代理并重开当前会话 |
| ping 成功，远端响应/数据长期不来 | 上游网络、服务器或认证 | 查最后阶段及脱敏 HTTP 分类；不要无条件重启代理 |
| 上游有数据，下游输出或播放位置不推进 | 下游消费、原生播放或缓存写入阻塞 | 区分转发、写盘与 native open 阶段 |
| `cache` pause/timeout 后同曲 relay 被 cancel | 任务所有权耦合 | 检查下载暂停是否取消了播放读取 |
| 同一票据长时间后再次请求被拒绝 | 本地票据到期 | 区分远端 403，合法会话换票后恢复 |
| 仅曲末/下一曲停住，出现 transition/open stalled | 切歌或打开流程 | 看前台状态、锁和原生操作完成/取消情况 |

用户后续观察可围绕：本地音频与 Emby、Wi-Fi 与移动网络、只播放与同时下载、曲中与切歌、普通熄屏与返回前台。无需预先假定必须连续六小时才会出现问题。

## 不应直接照搬的做法

- 不因参考 APK 中有广告、WorkManager、Alarm 或投屏服务，就认为这些是播放保活机制。
- 不复制参考软件给 SyncService / ReadMetadataService 声明 mediaPlayback 的做法来规避时限；我们应按实际任务选类型。
- 不把 JVM 线程、Kotlin 协程或独立进程当作自动豁免；独立进程反而需要新的身份、凭据、IPC 和资源关闭设计。
- 不依赖高频心跳维持系统存活；心跳用于诊断，不是保活授权。
- 不用固定睡眠替代确认旧连接/播放器操作已停止；参考软件的 2 秒/1 秒仅为样本实现细节。
- 不将“自动重试成功”“编译通过”表述为已经解决系统后台限制。

## 系统边界与来源

Android 的 `dataSync` / `mediaProcessing` 后台六小时时限与播放代理本身不是同一概念，也不是 Android 10 的该项限制；`mediaPlayback` 不在这项六小时时限的类型中。Doze、网络策略和厂商进程管理仍需分别分析。
